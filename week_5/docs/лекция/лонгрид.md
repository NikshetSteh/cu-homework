# Java 1. Неделя 5 — Наследование и полиморфизм

## Общая цель недели

На предыдущих неделях мы научились создавать классы, скрывать состояние объектов, распределять ответственность между несколькими объектами и задавать общие контракты через интерфейсы.

На этой неделе появляется следующий шаг: **несколько связанных классов могут работать через общий тип**.

Основная цепочка недели:

```text
родственные классы
↓
общий тип
↓
переопределение
↓
полиморфизм
```

После этой темы нужно понимать:

- как связать базовый и производный классы через `extends`;
- что означает отношение **«является»**;
- как инициализируется базовая часть объекта через `super(...)`;
- как переопределять методы через `@Override`;
- чем тип переменной отличается от реального типа объекта;
- что такое статическое и динамическое связывание;
- как полиморфизм позволяет писать общий алгоритм для разных реализаций;
- зачем нужны абстрактные классы и абстрактные методы;
- как работают восходящее и обратное приведение типов;
- когда использовать `instanceof`;
- чем наследование отличается от композиции;
- почему любой обычный класс связан с `Object`;
- чем `==` отличается от `equals()`;
- зачем нужен `hashCode()` и какой контракт связывает его с `equals()`.

# 2. От похожих классов к наследованию

Пусть сначала в программе существуют два независимых класса:

```java
class CourierDelivery {
    private String orderId;
    private String address;

    public int calculatePrice() {
        return 500;
    }
}
```

и:

```java
class ExpressDelivery {
    private String orderId;
    private String address;

    public int calculatePrice() {
        return 900;
    }
}
```

В этой модели заметны две вещи.

Во-первых, часть состояния повторяется:

```text
orderId
address
```

Во-вторых, у обоих классов есть одна и та же логическая операция:

```text
calculatePrice()
```

но правило её выполнения различается.

Прежде чем использовать наследование, важно задать вопрос:

```text
CourierDelivery является Delivery?
ExpressDelivery является Delivery?
```

Ответ — да.

Это разные разновидности одной сущности:

```text
             Delivery
            /        \
           /          \
CourierDelivery   ExpressDelivery
```

Такое отношение часто называют **is-a**:

```text
CourierDelivery is a Delivery
ExpressDelivery is a Delivery
```

То есть наследование имеет смысл не потому, что у двух классов случайно совпали поля, а потому, что один тип действительно является более конкретной разновидностью другого.

### Главное

```text
X является Y
↓
наследование может быть уместно
```

# 3. Базовый и производный классы

Выделим общий тип:

```java
class Delivery {
    private String orderId;
    private String address;
}
```

Конкретные виды доставки становятся наследниками:

```java
class CourierDelivery extends Delivery {
}
```

```java
class ExpressDelivery extends Delivery {
}
```

В конструкции:

```java
class CourierDelivery extends Delivery {
}
```

`Delivery` — базовый, или родительский, класс.

`CourierDelivery` — производный, или дочерний, класс.

Схема:

```text
Delivery
   ↑
   │
CourierDelivery
```

`CourierDelivery` является более конкретным типом `Delivery`.

---

## Что обычно выносят в базовый класс

В базовый класс помещают то, что является общим для всех наследников:

```text
BaseClass
├── общее состояние
├── общий конструктор
└── общее поведение
```

В наследниках остаются конкретные особенности.

Например:

```java
class CourierDelivery extends Delivery {
    private String district;
}
```

Получается:

```text
Delivery
→ общая часть

CourierDelivery
→ дополнительная часть
```

Наследник может добавлять:

- собственные поля;
- собственные методы;
- собственное поведение.

Не стоит помещать в базовый класс поля, которые нужны только отдельным наследникам.

### Главное

```text
базовый класс
→ общая часть модели

наследник
→ конкретные особенности
```

---

# 4. Конструкторы и `super(...)`

После переноса общих полей в базовый класс появляется проблема инициализации.

Пусть `Delivery` выглядит так:

```java
class Delivery {
    private String orderId;
    private String address;

    public Delivery(String orderId, String address) {
        this.orderId = orderId;
        this.address = address;
    }
}
```

А `CourierDelivery` добавляет собственное поле:

```java
class CourierDelivery extends Delivery {
    private String district;
}
```

Для создания `CourierDelivery` нужно задать:

```text
orderId
address
district
```

Но `orderId` и `address` принадлежат `Delivery`.

Их должен инициализировать сам базовый класс.

Для вызова конструктора родителя используется:

```java
super(...)
```

Пример:

```java
class CourierDelivery extends Delivery {
    private String district;

    public CourierDelivery(
            String orderId,
            String address,
            String district
    ) {
        super(orderId, address);
        this.district = district;
    }
}
```

Последовательность:

```text
super(orderId, address)
→ вызывает конструктор Delivery
→ передаёт orderId и address
→ Delivery инициализирует свою часть объекта
→ управление возвращается в CourierDelivery
→ CourierDelivery инициализирует district
```

Полная схема:

```text
new CourierDelivery(...)
↓
конструктор CourierDelivery
↓
super(...)
↓
конструктор Delivery
↓
инициализация общей части
↓
возврат в CourierDelivery
↓
инициализация части наследника
```

---

## Почему иногда появляется ошибка про no-arg constructor

Рассмотрим:

```java
public class Delivery {
    private String orderId;
    private String address;

    public Delivery(String orderId, String address) {
        this.orderId = orderId;
        this.address = address;
    }
}
```

и:

```java
public class ExpressDelivery extends Delivery {

    public int calculatePrice() {
        return 900;
    }
}
```

У `ExpressDelivery` нет явно написанного конструктора.

Java пытается создать конструктор автоматически:

```java
public ExpressDelivery() {
    super();
}
```

Но у `Delivery` нет конструктора без параметров:

```java
Delivery()
```

Есть только:

```java
Delivery(String orderId, String address)
```

Поэтому появляется ошибка:

```text
There is no no-arg constructor available in 'Delivery'
```

Исправление:

```java
public ExpressDelivery(
        String orderId,
        String address
) {
    super(orderId, address);
}
```

### Главное

Если родитель не имеет конструктора без параметров, наследник должен явно вызвать подходящий конструктор через `super(...)`.

---

## `this` и `super`

```text
this
→ текущий объект
```

```text
super(...)
→ конструктор родителя
```

```text
super.method()
→ метод родителя
```

# 5. `private` остаётся `private`

Наследование не отменяет инкапсуляцию.

```java
class Delivery {
    private String address;
}
```

Наследник не может напрямую обратиться к `address`:

```java
class CourierDelivery extends Delivery {

    public void changeAddress(String newAddress) {
        address = newAddress; // ошибка
    }
}
```

Причина:

```text
private
→ доступ только внутри класса,
в котором член объявлен
```

То есть:

```text
extends
→ связывает типы

private
→ продолжает защищать состояние
```

Если наследнику нужно получить значение, базовый класс может предоставить публичный метод:

```java
public String getAddress() {
    return address;
}
```

# 6. Переопределение методов

Для любой доставки нужно вычислить стоимость:

```text
calculatePrice()
```

Но правила разные:

```text
CourierDelivery
→ 500

ExpressDelivery
→ 900
```

Нужна одна общая операция с разными реализациями.

В базовом классе:

```java
class Delivery {
    public int calculatePrice() {
        return 0;
    }
}
```

В наследнике:

```java
class CourierDelivery extends Delivery {

    @Override
    public int calculatePrice() {
        return 500;
    }
}
```

В другом наследнике:

```java
class ExpressDelivery extends Delivery {

    @Override
    public int calculatePrice() {
        return 900;
    }
}
```

Получаем:

```text
Delivery.calculatePrice()
→ базовая реализация

CourierDelivery.calculatePrice()
→ 500

ExpressDelivery.calculatePrice()
→ 900
```

Это называется **переопределением метода** — overriding.

### Главное

```text
одна операция
+
разные реализации
```

---

# 7. `@Override`

`@Override` — аннотация.

Аннотации в Java начинаются с символа:

```text
@
```

Для текущей недели достаточно понимать аннотацию как дополнительную информацию о коде.

`@Override` сообщает компилятору:

> Этот метод должен переопределять метод родительского класса.

Например:

```java
@Override
public int calculatePrice() {
    return 500;
}
```

Если случайно написать:

```java
@Override
public int calculatePrices() {
    return 500;
}
```

компилятор обнаружит ошибку: такого метода у родителя нет.

Без `@Override` Java могла бы воспринять `calculatePrices()` как новый метод.

### Главное

`@Override` помогает проверить, что переопределение действительно произошло.

---

# 8. `super.method()`

Иногда наследник хочет не полностью заменить поведение родителя, а дополнить его.

```java
class Delivery {
    public void printInfo() {
        System.out.println("Delivery");
    }
}
```

```java
class CourierDelivery extends Delivery {

    @Override
    public void printInfo() {
        super.printInfo();
        System.out.println("Courier");
    }
}
```

При вызове:

```java
courierDelivery.printInfo();
```

получаем:

```text
CourierDelivery.printInfo()
↓
super.printInfo()
↓
Delivery.printInfo()
↓
возврат в CourierDelivery
↓
дополнительное поведение
```

# 9. Тип переменной и реальный тип объекта

Ключевой пример недели:

```java
Delivery delivery =
        new CourierDelivery(...);
```

Здесь:

```text
Delivery
→ тип переменной
```

```text
CourierDelivery
→ реальный тип объекта
```

Объект `CourierDelivery` можно хранить в переменной `Delivery`, потому что:

```text
CourierDelivery является Delivery
```

---

## Какие методы можно вызвать

Через переменную типа `Delivery` можно вызвать методы, известные `Delivery`:

```java
delivery.calculatePrice();
delivery.printInfo();
```

Но если метод существует только в `CourierDelivery`:

```java
delivery.getDistrict(); // ошибка
```

### Главное правило

```text
тип переменной
→ какие методы можно вызвать
```

Но для переопределённых методов этого недостаточно.

Нужно ещё определить, **какая конкретная реализация будет выполнена**.

---

# 10. Что такое связывание

**Связывание** — это выбор конкретного метода или реализации метода, которая будет вызвана.

Упрощённо:

```text
вызов метода
↓
Java определяет,
что именно выполнить
```

Для текущей темы полезно различать:

```text
статическое связывание
→ выбор во время компиляции
```

```text
динамическое связывание
→ выбор во время выполнения
```

Зачем это понимать?

Чтобы:

- предсказывать, какой метод действительно вызовется;
- не путать перегрузку и переопределение;
- понимать, почему базовая ссылка может запускать поведение наследника;
- понимать механизм полиморфизма.

---

# 11. Статическое связывание: перегрузка

Есть два метода с одинаковым именем, но разными параметрами:

```java
void printPrice(Delivery delivery) {
    System.out.println("Delivery");
}

void printPrice(CourierDelivery delivery) {
    System.out.println("CourierDelivery");
}
```

Это перегрузка — overloading.

Создаём:

```java
Delivery delivery =
        new CourierDelivery(...);

printPrice(delivery);
```

Результат:

```text
Delivery
```

Почему?

Тип переменной известен во время компиляции:

```text
delivery
→ Delivery
```

Поэтому компилятор выбирает:

```java
printPrice(Delivery)
```

ещё до запуска программы.

Схема:

```text
тип аргумента
→ Delivery
↓
компилятор выбирает перегрузку
↓
printPrice(Delivery)
```

### Главное

```text
overloading
→ compile time
→ статическое связывание
```

---

# 12. Динамическое связывание: переопределение

Теперь:

```java
class Delivery {
    public int calculatePrice() {
        return 0;
    }
}
```

и:

```java
class CourierDelivery extends Delivery {

    @Override
    public int calculatePrice() {
        return 500;
    }
}
```

Создаём:

```java
Delivery delivery =
        new CourierDelivery(...);
```

Вызываем:

```java
delivery.calculatePrice();
```

Компилятор сначала проверяет тип переменной:

```text
Delivery
```

и убеждается, что у `Delivery` есть метод:

```text
calculatePrice()
```

Значит, вызов допустим.

Но во время выполнения Java смотрит на реальный объект:

```text
CourierDelivery
```

и выбирает переопределённую реализацию:

```text
CourierDelivery.calculatePrice()
```

Результат:

```text
500
```

Схема:

```text
delivery.calculatePrice()
↓
тип переменной = Delivery
↓
вызов разрешён
↓
метод переопределён
↓
реальный объект = CourierDelivery
↓
CourierDelivery.calculatePrice()
```

Это называется **динамическим связыванием**.

### Главное

```text
реальный тип объекта
→ какая переопределённая реализация выполнится
```

---

## Статическое и динамическое связывание

| Статическое | Динамическое |
|---|---|
| выбор во время компиляции | выбор во время выполнения |
| пример: перегрузка | пример: переопределение |
| учитываются объявленные типы | учитывается реальный объект |

Коротко:

```text
overloading
→ compile time

overriding
→ runtime
```

---

# 13. Полиморфизм

Создадим:

```java
Delivery first =
        new CourierDelivery(...);

Delivery second =
        new ExpressDelivery(...);
```

Обе переменные имеют один общий тип:

```text
Delivery
```

Но реальные объекты разные:

```text
first
→ CourierDelivery

second
→ ExpressDelivery
```

Вызываем один и тот же метод:

```java
first.calculatePrice();
second.calculatePrice();
```

Получаем разное поведение.

Это и есть **полиморфизм** — возможность работать с разными объектами через общий тип и вызывать одну и ту же операцию, получая реализацию конкретного объекта.

```text
один общий тип
+
одна общая операция
+
разные реальные объекты
↓
разное поведение
```

---

# 14. Массив общего типа

Практическая польза полиморфизма особенно хорошо видна на массиве:

```java
Delivery[] deliveries = {
        new CourierDelivery(...),
        new ExpressDelivery(...),
        new CourierDelivery(...)
};
```

Теперь один цикл:

```java
for (Delivery delivery : deliveries) {
    System.out.println(
            delivery.calculatePrice()
    );
}
```

может обработать объекты разных классов.

В каждой итерации:

```text
тип переменной
→ Delivery

реальный объект
→ может быть разным
```

Поэтому каждый объект использует свою реализацию `calculatePrice()`.

---

## Без полиморфизма

Пришлось бы отдельно работать с конкретными типами:

```java
CourierDelivery[] courierDeliveries = {
        ...
};

ExpressDelivery[] expressDeliveries = {
        ...
};
```

и писать отдельную обработку:

```java
for (CourierDelivery delivery : courierDeliveries) {
    System.out.println(delivery.calculatePrice());
}

for (ExpressDelivery delivery : expressDeliveries) {
    System.out.println(delivery.calculatePrice());
}
```

Добавился новый тип?

```text
новый массив
+
новый цикл
+
изменение вызывающего кода
```

С полиморфизмом основной цикл остаётся прежним.

### Главное

```text
без полиморфизма
→ код знает конкретные типы

с полиморфизмом
→ код знает только общий тип
```

---

# 15. Восходящее приведение

```java
CourierDelivery courier =
        new CourierDelivery(...);

Delivery delivery = courier;
```

Это **восходящее приведение**, или upcasting.

```text
CourierDelivery
↓
Delivery
```

Оно безопасно, потому что:

```text
CourierDelivery является Delivery
```

Java обычно выполняет его автоматически.

---

## Реальный тип не меняется

После:

```java
Delivery delivery = courier;
```

сам объект не превращается в `Delivery`.

```text
реальный объект
→ CourierDelivery

тип переменной
→ Delivery
```

Меняется только тип ссылки, через которую мы работаем с объектом.

---

# 16. `instanceof` и обратное приведение

Пусть только у `CourierDelivery` есть:

```java
getDistrict()
```

Через `Delivery` этот метод вызвать нельзя:

```java
delivery.getDistrict(); // ошибка
```

Если нужно получить доступ к специфическому поведению, можно выполнить обратное приведение:

```java
CourierDelivery courier =
        (CourierDelivery) delivery;
```

Но оно небезопасно без проверки.

Например:

```java
Delivery delivery =
        new ExpressDelivery(...);

CourierDelivery courier =
        (CourierDelivery) delivery;
```

приведёт к ошибке во время выполнения.

Поэтому:

```java
if (delivery instanceof CourierDelivery) {
    CourierDelivery courier =
            (CourierDelivery) delivery;

    courier.getDistrict();
}
```

`instanceof` проверяет реальный тип объекта перед приведением.

---

## Много `instanceof` — повод проверить модель

Если код выглядит так:

```java
if (delivery instanceof CourierDelivery) {
    ...
} else if (delivery instanceof ExpressDelivery) {
    ...
} else if (delivery instanceof PickupDelivery) {
    ...
}
```

и все ветки отвечают на один вопрос:

```text
как посчитать стоимость?
```

то лучше использовать:

```java
delivery.calculatePrice();
```

### Главное

`instanceof` нужен, когда действительно требуется конкретный тип.

Но большое количество `instanceof` часто означает, что поведение лучше выразить через полиморфизм.

---

# 17. Абстрактные классы

Тип `Delivery` полезен как общий тип:

```java
Delivery[] deliveries = {
    new CourierDelivery(...),
    new ExpressDelivery(...)
};
```

Но имеет ли смысл:

```java
new Delivery(...)
```

если не существует конкретного правила доставки и расчёта цены?

Получаем:

```text
Delivery нужен как общий тип
↓
но объект Delivery сам по себе
не имеет смысла
```

Для этого используется:

```java
abstract class Delivery {
    private String orderId;
    private String address;
}
```

Теперь можно:

```java
Delivery delivery =
        new CourierDelivery(...);
```

но нельзя:

```java
new Delivery(...);
```

---

## Что может содержать абстрактный класс

```text
abstract class
├── поля
├── конструкторы
├── обычные методы
└── абстрактные методы
```

Например:

```java
abstract class Delivery {
    private String orderId;
    private String address;

    public Delivery(String orderId, String address) {
        this.orderId = orderId;
        this.address = address;
    }
}
```

Конструктор нужен, чтобы наследники могли инициализировать базовую часть:

```java
super(orderId, address);
```

---

# 18. Абстрактные методы

Раньше в `Delivery` было:

```java
public int calculatePrice() {
    return 0;
}
```

Но `return 0` — фиктивная реализация.

В реальной модели единого правила расчёта нет.

При этом любая доставка обязана уметь вычислять цену.

Поэтому метод можно сделать абстрактным:

```java
abstract class Delivery {
    public abstract int calculatePrice();
}
```

У абстрактного метода нет тела.

Он задаёт обязательную операцию:

```text
метод есть у всех
↓
общей реализации нет
↓
наследники обязаны реализовать
```

Например:

```java
class CourierDelivery extends Delivery {

    @Override
    public int calculatePrice() {
        return 500;
    }
}
```

### Главное

```text
общая операция существует
+
общей реализации нет
↓
abstract method
```

---

# 19. Полиморфизм через интерфейс

Полиморфизм работает не только через наследование классов.

Можно написать:

```java
PaymentProcessor processor =
        new CardPaymentProcessor();

processor.pay(1000);
```

Здесь:

```text
PaymentProcessor
→ интерфейс / общий тип

CardPaymentProcessor
→ конкретная реализация
```

Принцип тот же:

```text
общий тип
↓
разные реализации
↓
одинаковый вызов
↓
разное поведение
```

---

# 20. `abstract class` vs `interface`

| `abstract class` | `interface` |
|---|---|
| общая основа родственных классов | общий контракт поведения |
| может хранить состояние | обычно не хранит состояние объекта |
| может иметь конструктор | конструктора нет |
| может содержать реализацию | реализацию дают классы |
| может содержать abstract-методы | задаёт обязательные операции |
| один базовый класс | интерфейсов может быть несколько |
| хорошо подходит для «является» | хорошо подходит для «умеет / поддерживает контракт» |

Пример:

```text
CourierDelivery является Delivery
→ наследование / abstract class
```

```text
CardPaymentProcessor умеет pay()
BonusPaymentProcessor умеет pay()
→ interface
```

# 21. Наследование или композиция

Наследование:

```text
X является Y
```

Например:

```text
CourierDelivery является Delivery
Dog является Animal
```

Композиция:

```text
X содержит / использует Y
```

Например:

```java
public class ExpressDelivery {
    private Courier courier;
}
```

Здесь:

```text
ExpressDelivery использует Courier
```

но:

```text
ExpressDelivery не является Courier
```

---

## Плохая модель

```java
class Car extends Engine {
}
```

Проблема:

```text
Car не является Engine
```

Правильнее:

```java
class Car {
    private Engine engine;
}
```

потому что:

```text
Car содержит Engine
```

---

## Не наследуемся только ради кода

Плохая мотивация:

```text
«там уже есть нужный метод»
↓
extends
```

Правильный вопрос:

```text
является ли X разновидностью Y?
```

Если нет:

```text
композиция
или интерфейс
```

# 22. Риски чрезмерного наследования

Наследование полезно, но создаёт сильную связь между классами.

Основные риски:

- наследник зависит от родителя;
- изменение базового класса влияет на наследников;
- глубокие иерархии трудно читать;
- неправильное `extends` портит модель;
- большое количество `instanceof` может быть сигналом плохого проектирования.

Простая цепочка:

```text
Object
↑
Delivery
↑
CourierDelivery
```

обычно понятнее, чем:

```text
Object
↑
Delivery
↑
PhysicalDelivery
↑
CityDelivery
↑
FastCityCourierDelivery
```

---

# 23. `Object` — корень иерархии

Если родитель явно не указан:

```java
class Delivery {
}
```

Java всё равно включает класс в общую иерархию.

Упрощённо можно думать так:

```java
class Delivery extends Object {
}
```

`Object` — базовый класс для всех обычных классов Java.

Иерархия:

```text
Object
  ↑
Delivery
  ↑
CourierDelivery
```

Объект `CourierDelivery` одновременно является:

```text
CourierDelivery
Delivery
Object
```

---

# 24. Методы `Object`

Все классы получают базовые методы `Object`.

| Метод | Назначение |
|---|---|
| `toString()` | строковое представление объекта |
| `equals(Object other)` | смысловое сравнение объектов |
| `hashCode()` | хеш-код объекта |
| `getClass()` | реальный класс объекта |
| `clone()` | копирование; отдельная тема |
| `wait()` / `notify()` / `notifyAll()` | многопоточность |
| `finalize()` | устаревший механизм, использовать не нужно |

На этой неделе важны прежде всего:

```text
toString()
equals()
hashCode()
getClass()
```

---

# 25. `toString()` и `getClass()`

Когда мы пишем:

```java
@Override
public String toString() {
    return "Delivery{...}";
}
```

мы переопределяем метод:

```text
Object.toString()
```

То есть `toString()` не создаётся «с нуля».

---

Метод:

```java
getClass()
```

показывает реальный класс объекта.

```java
Delivery delivery =
        new CourierDelivery(...);

System.out.println(
        delivery.getClass()
);
```

Тип переменной:

```text
Delivery
```

Реальный класс:

```text
CourierDelivery
```

---

# 26. `Object` как тип переменной

Можно написать:

```java
Object value =
        new CourierDelivery(...);
```

Поскольку любой `CourierDelivery` является `Object`.

Но через `Object` доступны только методы, известные `Object`.

Можно:

```java
value.toString();
value.getClass();
```

Нельзя:

```java
value.calculatePrice();
```

Снова работает правило:

```text
тип переменной
→ определяет доступные методы
```

---

# 27. `==` и `equals()`

Для объектов:

```java
first == second
```

проверяет:

```text
это одна и та же ссылка?
```

А:

```java
first.equals(second)
```

может проверять:

```text
считаются ли объекты равными
по правилам класса?
```

То есть:

```text
==
→ идентичность ссылки

equals()
→ смысловое равенство
```

---

# 28. `equals()` приходит из `Object`

Метод:

```java
equals(Object other)
```

уже существует в `Object`.

Собственный класс может переопределить его и определить:

```text
что означает
«эти два объекта равны»
```

Например, можно считать две доставки равными:

- только по `orderId`;
- по `orderId` и `address`;
- по другому набору значимых полей.

Это решение зависит от предметной модели.

---

# 29. Пример смыслового равенства

Пусть две доставки считаются равными, если совпадает `orderId`.

```java
Delivery first =
        new CourierDelivery("A-101", ...);

Delivery second =
        new CourierDelivery("A-101", ...);
```

Это разные объекты:

```text
first == second
→ false
```

Но:

```text
first.equals(second)
→ true
```

если `equals()` определён по `orderId`.

---

# 30. Контракт `equals()`

Корректный `equals()` должен соблюдать несколько свойств.

### Рефлексивность

```text
a.equals(a) → true
```

### Симметричность

```text
a.equals(b) == b.equals(a)
```

### Транзитивность

```text
если a равно b
и b равно c
→ a равно c
```

### Стабильность

Если данные не меняются, результат `equals()` не должен неожиданно меняться.

### `null`

```text
a.equals(null) → false
```

---

# 31. Пример `equals()` по всем значимым полям

Пусть `CourierDelivery` сравнивается по:

```text
orderId
address
```

Тогда:

```java
@Override
public boolean equals(Object obj) {
    if (this == obj) {
        return true;
    }

    if (obj == null || getClass() != obj.getClass()) {
        return false;
    }

    CourierDelivery other =
            (CourierDelivery) obj;

    return getOrderId().equals(other.getOrderId())
            && getAddress().equals(other.getAddress());
}
```

Логика:

```text
тот же объект?
→ true

null или другой класс?
→ false

иначе
→ сравниваем значимые поля
```

---

# 32. `hashCode()`

Метод:

```java
int hashCode()
```

возвращает целое число:

```text
объект
↓
hashCode()
↓
int
```

Хеш-структуры:

```text
HashSet
HashMap
```

используют его как быстрый ориентир при поиске.

Упрощённо:

```text
объект
↓
hashCode()
↓
определяем область поиска
↓
при необходимости equals()
↓
проверяем конкретный объект
```

Подробно `HashSet` и `HashMap` будут разобраны на неделе коллекций.

### Главное

`hashCode()` помогает ускорить поиск, но сам по себе не определяет равенство объектов.

---

# 33. `hashCode()` не уникален

Допустимо:

```text
a.hashCode() == b.hashCode()
```

при этом:

```text
a.equals(b) == false
```

То есть:

```text
одинаковый hashCode
↛
равные объекты
```

Такие совпадения называются коллизиями.

---

# 34. Контракт `equals()` и `hashCode()`

Если:

```text
a.equals(b) == true
```

то обязательно:

```text
a.hashCode() == b.hashCode()
```

Схема:

```text
equals() → true
↓
одинаковый hashCode
```

Но обратное правило не работает:

```text
одинаковый hashCode
↛
equals() == true
```

---

# 35. Одни и те же поля для равенства и хеша

Если равенство определяется по:

```text
orderId
```

то:

```text
equals()
→ сравнивает orderId

hashCode()
→ считается по orderId
```

Если `equals()` сравнивает:

```text
orderId + address
```

то `hashCode()` должен учитывать те же поля.

Например:

```java
@Override
public int hashCode() {
    int result = getOrderId().hashCode();
    result = 31 * result + getAddress().hashCode();
    return result;
}
```

На текущем этапе важно не число `31`, а принцип:

```text
поля равенства
↓
equals()
+
hashCode()
```

---

# 36. Ошибка: переопределили только `equals()`

Если:

```java
@Override
public boolean equals(Object other) {
    // сравнение по orderId
}
```

но `hashCode()` не переопределён, может получиться:

```text
first.equals(second)
→ true

first.hashCode() != second.hashCode()
→ возможно
```

Контракт нарушен.

Поэтому практическое правило:

```text
переопределяем equals()
↓
переопределяем hashCode()
```

IDE умеет генерировать оба метода:

```text
Generate
→ equals() and hashCode()
```

Но разработчик всё равно должен сам определить, какие поля задают равенство.
