# Java 1. Неделя 6 — Исключения

## Исключения как отдельный путь выполнения программы

До сих пор большинство методов в наших программах работали по простой модели:

```text
получили данные
↓
выполнили операцию
↓
вернули результат
```

Например:

```java
public static int parseAge(String text) {
    return Integer.parseInt(text);
}
```

Если передать строку `"18"`, всё работает ожидаемо:

```text
"18"
↓
18
```

Но что произойдёт, если передать:

```text
"abc"
```

Метод `Integer.parseInt(...)` не может получить корректное число. Он не может вернуть `18`, `0` или какое-то другое специальное значение: любое такое число могло бы быть настоящим результатом.

Вместо обычного результата возникает:

```text
NumberFormatException
```

Это и есть первый важный смысл исключений:

> Исключение позволяет сообщить, что текущая операция не смогла завершиться обычным способом.

У метода оказывается два возможных пути завершения:

```text
метод
├── обычное завершение
└── исключительное завершение
```

Исключение не означает автоматически «программа сломалась навсегда». Оно означает, что **текущая операция не смогла продолжить обычный сценарий**. Дальше программа может либо обработать эту ситуацию, либо передать её выше.

---

# 1. Что такое исключение

**Исключение (`exception`)** — это объект Java, который сообщает, что во время выполнения программы произошла ситуация, из-за которой текущая операция не может продолжиться обычным способом.

Общая модель:

```text
проблема во время выполнения
↓
создаётся объект исключения
↓
обычный путь выполнения прерывается
↓
исключение передаётся для обработки
```

Важно, что исключение — именно **объект**, а не просто текст вроде `"Error"`.

Объект исключения содержит информацию о проблеме:

```text
exception
├── тип исключения
├── сообщение
└── stack trace
```

Например, если выполнить:

```java
Integer.parseInt("abc");
```

можно получить исключение типа:

```text
NumberFormatException
```

Его сообщение может содержать дополнительную информацию:

```text
For input string: "abc"
```

А stack trace показывает, где исключение возникло и через какие вызовы программа пришла в эту точку.

### Главное

```text
exception
→ объект Java
→ описывает проблему
→ прерывает обычный путь выполнения
```

# 2. Stack trace: как найти место ошибки

Рассмотрим программу:

```java
public class Main {

    public static void main(String[] args) {
        int age = parseAge("abc");
        System.out.println(age);
    }

    public static int parseAge(String text) {
        return Integer.parseInt(text);
    }
}
```

Код компилируется.

Но во время выполнения `Integer.parseInt("abc")` выбрасывает `NumberFormatException`.

Если исключение никто не обработал, Java выводит stack trace.

Упрощённо он может выглядеть так:

```text
java.lang.NumberFormatException: For input string: "abc"
    at java.lang.Integer.parseInt(...)
    at Main.parseAge(Main.java:9)
    at Main.main(Main.java:4)
```

Stack trace стоит читать по частям.

## Тип исключения

```text
NumberFormatException
```

Он отвечает на вопрос:

> Что произошло?

## Сообщение

```text
For input string: "abc"
```

Оно даёт дополнительную информацию о конкретной причине.

## Место возникновения

```text
at Integer.parseInt(...)
```

Именно там исключение было создано и выброшено.

## Цепочка вызовов

```text
at Main.parseAge(...)
at Main.main(...)
```

Она показывает, через какие методы программа пришла к проблемной операции.

Можно представить это так:

```text
main()
↓ вызывает
parseAge()
↓ вызывает
Integer.parseInt(...)
↓
NumberFormatException
```

В самом stack trace этот путь показывается начиная с места возникновения исключения:

```text
NumberFormatException
↓
Integer.parseInt(...)
↓
parseAge(...)
↓
main(...)
```

### Практический алгоритм чтения

Когда видите stack trace:

1. найдите **тип исключения**;
2. прочитайте **сообщение**;
3. найдите первую строку, которая относится к **вашему коду**;
4. восстановите цепочку вызовов.

Не нужно сразу пытаться понять десятки строк библиотечного кода.

### Главное

> Stack trace показывает не только место ошибки, но и путь вызовов, по которому программа к ней пришла.

# 3. Что происходит без обработчика

Когда возникает исключение, обычное выполнение текущей операции прекращается.

Если подходящего обработчика нет:

```text
исключение возникло
↓
обработчика нет
↓
текущая операция прервана
↓
исключение передаётся выше
↓
программа может завершиться
```

Например:

```java
public static void main(String[] args) {
    int age = Integer.parseInt("abc");

    System.out.println("После преобразования");
}
```

Строка:

```java
System.out.println("После преобразования");
```

не выполнится.

Причина проста:

```text
Integer.parseInt("abc")
↓
NumberFormatException
↓
обычный путь main() прерван
```

Если мы знаем, что делать в такой ситуации, исключение можно обработать.

---

# 4. `try-catch`: обработка исключения

Для обработки используется конструкция `try-catch`.

```java
try {
    int age = Integer.parseInt(text);
    System.out.println(age);

} catch (NumberFormatException e) {
    System.out.println("Некорректный возраст");
}
```

Здесь две части.

## `try`

В `try` помещается код, при выполнении которого мы ожидаем конкретную проблему:

```java
try {
    int age = Integer.parseInt(text);
}
```

## `catch`

`catch` описывает реакцию на определённый тип исключения:

```java
catch (NumberFormatException e) {
    System.out.println("Некорректный возраст");
}
```

Общая схема:

```text
try
↓
исключения нет
→ обычное продолжение

исключение есть
↓
подходящий catch
↓
обработка
↓
продолжение программы
```

Например:

```java
public static void printAge(String text) {
    try {
        int age = Integer.parseInt(text);
        System.out.println("Возраст: " + age);

    } catch (NumberFormatException e) {
        System.out.println("Возраст должен быть числом");
    }

    System.out.println("Метод завершён");
}
```

Для:

```java
printAge("18");
```

получим:

```text
Возраст: 18
Метод завершён
```

Для:

```java
printAge("abc");
```

получим:

```text
Возраст должен быть числом
Метод завершён
```

Почему последняя строка выполняется во втором случае?

Потому что `NumberFormatException` был перехвачен подходящим `catch`.

### Важный момент

Сам факт наличия `catch` ещё не означает, что ошибка обработана хорошо.

Например:

```java
catch (NumberFormatException e) {
}
```

исключение технически перехвачено, но программа просто потеряла информацию о проблеме.

Обработка должна иметь смысл для текущего сценария.

---

# 5. Объект исключения внутри `catch`

Посмотрим ещё раз на:

```java
catch (NumberFormatException e) {
    ...
}
```

Здесь:

```text
NumberFormatException
→ тип переменной

e
→ ссылка на объект исключения
```

То есть знания об объектах из предыдущих недель напрямую применяются к исключениям.

У объекта исключения можно получить полезную информацию.

| Метод | Что делает |
|---|---|
| `getMessage()` | возвращает сообщение об ошибке |
| `getClass()` | возвращает реальный класс объекта |
| `printStackTrace()` | печатает stack trace |
| `getStackTrace()` | возвращает stack trace как данные |
| `getCause()` | возвращает причину исключения, если она есть |

Пример:

```java
try {
    Integer.parseInt("abc");

} catch (NumberFormatException e) {
    System.out.println(e.getMessage());
    System.out.println(e.getClass());
    e.printStackTrace();
}
```

В учебных задачах чаще всего достаточно понимать:

```text
getMessage()
→ описание проблемы

getClass()
→ тип исключения

printStackTrace()
→ вывести цепочку вызовов
```

`getCause()` и `getStackTrace()` важно узнавать, но подробно работать с ними на этой неделе не требуется.

# 6. `try` лучше делать узким

Рассмотрим вариант:

```java
try {
    String name = "Anna";

    int age = Integer.parseInt(ageText);

    if (age < 18) {
        System.out.println("Too young");
    }

    Participant participant =
            new Participant(name, age);

    System.out.println(participant);

} catch (NumberFormatException e) {
    System.out.println("Некорректный возраст");
}
```

Здесь `NumberFormatException` ожидается прежде всего от:

```java
Integer.parseInt(ageText);
```

Но внутри `try` находится гораздо больше кода.

Это ухудшает читаемость:

```text
большой try
↓
не сразу понятно,
какая операция считается опасной
```

Часто лучше сузить область:

```java
int age;

try {
    age = Integer.parseInt(ageText);

} catch (NumberFormatException e) {
    System.out.println("Некорректный возраст");
    return;
}

Participant participant =
        new Participant("Anna", age);

System.out.println(participant);
```

Теперь граница очевидна:

```text
try
→ только операция,
которая может выбросить
ожидаемое исключение
```

Это не значит, что `try` всегда должен содержать ровно одну строку. Важно другое:

> В `try` стоит оставлять тот фрагмент, который относится к обрабатываемому ошибочному сценарию.

# 7. Исключения встроены в иерархию классов Java

Исключения — обычные объекты, поэтому у них есть наследование.

Основная верхняя часть иерархии:

```text
Object
↓
Throwable
├── Error
└── Exception
```

## `Throwable`

`Throwable` — базовый класс для объектов, которые могут участвовать в механизме исключений.

Именно от него идут две важные ветки:

```text
Throwable
├── Error
└── Exception
```

## `Error`

`Error` описывает серьёзные проблемы среды выполнения, которые приложение обычно не рассматривает как обычные прикладные сценарии.

Примеры:

- `OutOfMemoryError` — JVM не смогла выделить необходимую память;
- `StackOverflowError` — переполнен стек вызовов, например из-за бесконечной рекурсии.

## `Exception`

`Exception` — основная ветка исключительных ситуаций, с которыми работает прикладной код.

Примеры:

- `NumberFormatException`;
- `IllegalArgumentException`;
- `IOException`;
- собственные исключения приложения.

Упрощённая модель:

```text
Throwable
├── Error
└── Exception
    ├── RuntimeException
    │   ├── NullPointerException
    │   ├── IllegalArgumentException
    │   └── NumberFormatException
    │
    └── другие Exception
```

Эта иерархия важна ещё и потому, что `catch` работает с типами.

# 8. Один `try` — несколько `catch`

Один фрагмент кода может завершиться разными исключениями.

Например:

```java
try {
    int value = Integer.parseInt(text);
    System.out.println(100 / value);

} catch (NumberFormatException e) {
    System.out.println("Не число");

} catch (ArithmeticException e) {
    System.out.println("Деление на ноль");
}
```

Если:

```text
text = "abc"
```

то:

```text
Integer.parseInt("abc")
↓
NumberFormatException
↓
первый catch подходит
↓
"Не число"
```

Если:

```text
text = "0"
```

то:

```text
Integer.parseInt("0")
↓
0
↓
100 / 0
↓
ArithmeticException
↓
второй catch
↓
"Деление на ноль"
```

Java проверяет обработчики сверху вниз и выбирает первый подходящий по типу.

Поэтому более конкретные обработчики располагают выше более общих.

Например:

```text
NumberFormatException
↓
RuntimeException
↓
Exception
```

Если поставить:

```java
catch (Exception e) {
    ...
}
```

раньше `catch (NumberFormatException e)`, общий обработчик уже подходит для `NumberFormatException`, поэтому более конкретный обработчик ниже становится недостижимым.

### Главное

> Чем точнее тип в `catch`, тем понятнее, какую именно проблему этот код умеет обрабатывать.

# 9. Checked и unchecked exceptions

Теперь можно разделить исключения на две важные группы.

Это различие связано прежде всего с **требованиями компилятора**.

## Unchecked exceptions

К unchecked относятся `RuntimeException` и его наследники.

Примеры:

```text
RuntimeException
├── NullPointerException
├── IllegalArgumentException
└── NumberFormatException
```

### `NullPointerException`

Возникает, когда код пытается обратиться к объекту через `null`.

```java
String name = null;

System.out.println(name.length());
```

Код компилируется, но во время выполнения возникает `NullPointerException`.

### `IllegalArgumentException`

Обычно используется, когда методу передали аргумент, нарушающий его правила.

```java
public static void setAge(int age) {
    if (age < 0) {
        throw new IllegalArgumentException(
                "Age must be non-negative"
        );
    }
}
```

### `NumberFormatException`

Возникает, если строку нельзя преобразовать в требуемый числовой формат.

```java
int age = Integer.parseInt("abc");
```

## Что значит unchecked

Компилятор не требует обязательно писать:

```text
catch
или
throws
```

Например:

```java
int value = Integer.parseInt(text);
```

может выбросить `NumberFormatException`, но этот код можно написать без `try-catch`.

То же самое:

```java
String name = null;
System.out.println(name.length());
```

Компилятор не заставит нас заранее обрабатывать `NullPointerException`.

Важно:

> Unchecked означает «компилятор не требует обязательной обработки», а не «исключение не может возникнуть».

# 10. Checked exceptions

Для checked-исключений компилятор требует явного решения.

Упрощённо:

```text
checked exception
↓
catch
или
throws
```

То есть вызывающий код должен:

1. обработать исключение;
2. или передать ответственность выше.

В качестве знакомого примера checked-исключения можно использовать собственный тип:

```java
public class RegistrationException
        extends Exception {
}
```

Если метод объявляет:

```java
public static void register(int age)
        throws RegistrationException {

    if (age < 14) {
        throw new RegistrationException();
    }
}
```

то простой вызов:

```java
register(10);
```

уже требует решения со стороны вызывающего кода.

Первый вариант — обработать:

```java
try {
    register(10);

} catch (RegistrationException e) {
    System.out.println("Регистрация невозможна");
}
```

Второй вариант — передать дальше:

```java
public static void process()
        throws RegistrationException {

    register(10);
}
```

Из стандартной библиотеки типичным checked-исключением является `FileNotFoundException`.

На следующей неделе мы подробно познакомимся с файлами, но уже сейчас важно увидеть сам механизм:

```java
public static void openData()
        throws FileNotFoundException {
    // операция, которая может не найти файл
}
```

Вызывающий код должен учесть эту возможность.

## Checked vs unchecked

| Checked | Unchecked |
|---|---|
| компилятор требует `catch` или `throws` | такого требования нет |
| возможность явно отражается в контракте метода | исключение может возникнуть без объявления |
| наследники `Exception`, кроме ветки `RuntimeException` | `RuntimeException` и его наследники |

Главное техническое различие:

```text
checked
→ компилятор требует решения

unchecked
→ компилятор не требует решения
```

Это не означает:

```text
checked
→ серьёзные

unchecked
→ несерьёзные
```

Серьёзность проблемы и правило компилятора — разные вещи.

# 11. `throw`: выбрасываем исключение сами

До этого исключения часто возникали внутри Java API.

Например:

```java
Integer.parseInt("abc");
```

Но наш собственный код тоже может обнаружить ситуацию, в которой текущую операцию нельзя продолжать.

Для этого используется `throw`.

```java
public static void setAge(int age) {
    if (age < 0) {
        throw new IllegalArgumentException(
                "Age must be non-negative"
        );
    }

    System.out.println("Age accepted");
}
```

Здесь важно разделить две операции:

```text
new IllegalArgumentException(...)
→ создать объект исключения

throw
→ выбросить этот объект
```

## Что происходит после `throw`

Рассмотрим:

```java
public static void process(int value) {
    System.out.println("Шаг 1");

    if (value < 0) {
        throw new IllegalArgumentException(
                "value < 0"
        );
    }

    System.out.println("Шаг 2");
    System.out.println("Шаг 3");
}
```

Вызов:

```java
process(-5);
```

идёт так:

```text
"Шаг 1"
↓
value < 0
↓
throw
↓
текущий обычный путь прерывается
```

Строки:

```text
Шаг 2
Шаг 3
```

уже не выполняются.

После `throw` Java начинает искать подходящий обработчик.

### Главное

> `throw` — это действие во время выполнения, которое запускает исключительный путь.

---

# 12. `throws`: предупреждение в сигнатуре метода

`throw` и `throws` легко перепутать из-за похожих названий.

Но смысл у них разный.

Пример:

```java
public static void register()
        throws RegistrationException {
    ...
}
```

`throws` можно читать так:

> Этот метод может завершиться `RegistrationException`.

Само слово `throws` ничего не выбрасывает в момент объявления.

Оно сообщает вызывающему коду о возможном исключении.

## Сравнение

| `throw` | `throws` |
|---|---|
| выбрасывает конкретное исключение | объявляет возможность исключения |
| используется внутри метода | пишется в сигнатуре |
| работает с объектом исключения | указывает тип исключения |
| срабатывает во время выполнения | описывает контракт метода |
| прерывает обычный путь | само по себе ничего не прерывает |

Коротко:

```text
throw
→ выбросить

throws
→ предупредить
```

# 13. Распространение исключения по цепочке вызовов

Метод, где возникла ошибка, не обязан сам её обрабатывать.

Рассмотрим:

```java
public static int parseAge(String text) {
    return Integer.parseInt(text);
}

public static Student createStudent(
        String name,
        String ageText
) {
    int age = parseAge(ageText);

    return new Student(name, age);
}

public static void registerStudent(
        String name,
        String ageText
) {
    try {
        Student student =
                createStudent(name, ageText);

        System.out.println(
                "Registered: " + student
        );

    } catch (NumberFormatException e) {
        System.out.println(
                "Не удалось зарегистрировать студента: "
                        + "возраст указан неверно"
        );
    }
}
```

Цепочка вызовов:

```text
registerStudent()
↓
createStudent()
↓
parseAge()
↓
Integer.parseInt(...)
↓
NumberFormatException
```

Исключение возникает внутри:

```text
Integer.parseInt(...)
```

Но там нет информации о сценарии регистрации.

`parseAge()` знает:

```text
строку нельзя преобразовать в число
```

`createStudent()` знает:

```text
объект Student создать не удалось
```

А `registerStudent()` знает:

```text
нужно отменить регистрацию
и сообщить понятную причину
```

Поэтому именно верхний уровень может быть лучшим местом для обработки.

## Что происходит, если `catch` нет

Если текущий метод не ловит исключение:

```text
исключение
↓
обычный путь метода прекращается
↓
исключение передаётся вызывающему методу
```

Так продолжается вверх:

```text
Integer.parseInt(...)
↓ exception

parseAge()
↓ catch нет

createStudent()
↓ catch нет

registerStudent()
↓ catch найден
```

Такое движение называют **распространением исключения по цепочке вызовов**.

## Где лучше ставить `catch`

Хорошее правило:

> Обрабатывать исключение стоит там, где коду уже хватает контекста, чтобы принять осмысленное решение.

Место возникновения и место обработки могут быть разными.

---

# 14. Две крайности при обработке исключений

## Слишком низкий уровень

Представим:

```java
public static int parseAge(String text) {
    try {
        return Integer.parseInt(text);

    } catch (NumberFormatException e) {
        System.out.println("Ошибка");
        return 0;
    }
}
```

Проблема не только в возвращаемом `0`.

Главное — `parseAge()` не знает, что происходило в приложении:

```text
регистрация?
редактирование профиля?
импорт данных?
```

Он знает только технический факт:

```text
строка не является числом
```

Если низкоуровневый метод сам решает, что вывести пользователю и как продолжать сценарий, ответственность оказывается не на своём уровне.

## Слишком высокий уровень

Другая крайность:

```java
public static void main(String[] args) {
    try {
        // почти вся программа
    } catch (Exception e) {
        System.out.println("Что-то пошло не так");
    }
}
```

Проблемы:

- разные ошибки смешиваются;
- неясно, какая операция могла упасть;
- трудно выбрать разную реакцию;
- общий `catch` может перехватить то, что мы не умеем корректно обрабатывать.

Лучше:

```text
ошибка возникает
↓
при необходимости распространяется выше
↓
обрабатывается там,
где понятна реакция
```

---

# 15. Exception или обычный результат?

Очень важный вопрос:

> Нужно ли вообще использовать исключение?

Не каждая неудачная ситуация является исключительной.

## Обычный ожидаемый исход

Например:

```java
public boolean withdraw(int amount) {
    ...
}
```

По контракту метода оба результата могут быть нормальными:

```text
денег хватает
→ списали
→ true

денег не хватает
→ ничего не изменили
→ false
```

Недостаток денег здесь может быть обычным ожидаемым исходом операции.

Тогда `boolean` вполне подходит.

## Когда исключение уместно

Теперь другой пример:

```java
setAge(-20);
```

Если контракт метода говорит:

```text
age >= 0
```

значение `-20` нарушает правила метода.

Можно написать:

```java
public void setAge(int age) {
    if (age < 0) {
        throw new IllegalArgumentException(
                "Age must be non-negative"
        );
    }

    this.age = age;
}
```

Здесь нормального результата операции нет:

```text
корректный аргумент
→ метод выполняет работу

контракт нарушен
→ обычное продолжение невозможно
→ exception
```

## Практический вопрос выбора

Спросите:

> Эта ситуация является нормальным ожидаемым исходом операции?

Если да:

```text
обычное управление потоком
→ if / return / boolean
```

Если нет:

```text
операция не может
корректно продолжиться
→ exception
```

Примеры:

| Ситуация | Возможный подход |
|---|---|
| товар не найден при обычном поиске | обычный результат: `null`, `boolean` и т. п. |
| денег недостаточно для снятия | `false` |
| возраст передан как `-20` | `IllegalArgumentException` |
| `"abc"` преобразуется в `int` | `NumberFormatException` |
| операция нарушает свой контракт | exception |

Одна и та же ситуация в разных программах может иметь разные контракты.

Поэтому универсального правила «всегда бросать exception при ошибке» нет.

### Главное

> Exception — не замена `if`. Исключение используется, когда обычный сценарий текущей операции нельзя корректно продолжить.

# 16. Зачем нужны собственные исключения

Стандартные исключения хорошо описывают технические проблемы:

```text
NumberFormatException
→ строку нельзя преобразовать в число

NullPointerException
→ обращение через null

IllegalArgumentException
→ некорректный аргумент
```

Но приложение имеет собственные правила.

Например:

```text
регистрация запрещена
заказ нельзя подтвердить
билет уже продан
лимит бронирования превышен
```

Можно написать:

```java
throw new Exception(
        "Registration failed"
);
```

Но тип `Exception` почти ничего не говорит о смысле проблемы.

Гораздо выразительнее:

```java
throw new RegistrationException(
        "Student is too young"
);
```

Теперь уже сам тип сообщает:

```text
RegistrationException
→ проблема связана
с регистрацией
```

## Разные проблемы — разные типы

Допустим, регистрация может завершиться так:

```text
возраст меньше допустимого
→ RegistrationException

мест нет
→ CourseFullException

участник уже зарегистрирован
→ AlreadyRegisteredException
```

Это позволяет вызывающему коду различать ситуации не по тексту сообщения, а по типу исключения.

Плохо:

```java
throw new Exception("COURSE_FULL");
```

Лучше:

```java
throw new CourseFullException(
        "No places available"
);
```

Тип становится частью смысла программы.

---

# 17. Как создать собственное исключение

Собственное исключение — обычный класс-наследник.

Например checked-исключение:

```java
public class RegistrationException
        extends Exception {

    public RegistrationException(
            String message
    ) {
        super(message);
    }
}
```

Здесь используются уже знакомые механизмы:

```text
RegistrationException
↓ extends
Exception
```

Конструктор:

```java
super(message);
```

передаёт сообщение базовому классу.

Теперь исключение можно выбросить:

```java
public static void register(int age)
        throws RegistrationException {

    if (age < 14) {
        throw new RegistrationException(
                "Student is too young"
        );
    }

    System.out.println("Registered");
}
```

Важно:

> Мы не создаём новый механизм ошибок. Мы создаём новый тип внутри уже существующей иерархии исключений Java.

Собственный тип можно наследовать и от `RuntimeException`, если по дизайну нужен unchecked-вариант. На этой неделе важнее понять сам принцип выбора типа, а не строить большие иерархии исключений.

# 18. Зачем отдельный тип вызывающему коду

Представим метод:

```java
registerStudent(...);
```

Если он может выбросить:

```text
RegistrationException
```

вызывающий код может обработать именно проблему регистрации:

```java
try {
    registerStudent(...);

} catch (RegistrationException e) {
    System.out.println(
            "Регистрация невозможна: "
                    + e.getMessage()
    );
}
```

Если типов несколько:

```java
try {
    registerStudent(...);

} catch (AlreadyRegisteredException e) {
    System.out.println(
            "Участник уже зарегистрирован"
    );

} catch (CourseFullException e) {
    System.out.println(
            "В группе больше нет мест"
    );
}
```

Получается:

```text
разные проблемы приложения
↓
разные типы исключений
↓
разная реакция вызывающего кода
```

Собственные исключения особенно полезны, когда нужно:

- точно назвать проблему предметной области;
- отличать одну прикладную ошибку от другой;
- сделать контракт метода понятнее;
- позволить вызывающему коду выбрать разную реакцию.

### Главное

> Хороший тип собственного исключения отвечает на вопрос: «Что именно не удалось сделать в нашем приложении?»

# 19. `finally`: завершающее действие

Иногда есть код, который должен выполниться после операции независимо от того, была ошибка или нет.

Рассмотрим:

```java
System.out.println("Начинаем операцию");

int value = Integer.parseInt(text);

System.out.println("Завершаем операцию");
```

Если:

```text
text = "abc"
```

возникает `NumberFormatException`.

До:

```java
System.out.println("Завершаем операцию");
```

код уже не дойдёт.

Схема:

```text
операция началась
↓
возникло исключение
↓
обычный путь прерван
↓
завершающий код пропущен
```

Для общего завершающего шага используется `finally`.

```java
try {
    System.out.println("Start");

    int value = Integer.parseInt(text);

    System.out.println("Value: " + value);

} catch (NumberFormatException e) {
    System.out.println("Некорректное число");

} finally {
    System.out.println("Finish");
}
```

Если:

```text
text = "42"
```

получим:

```text
Start
Value: 42
Finish
```

Если:

```text
text = "abc"
```

получим:

```text
Start
Некорректное число
Finish
```

То есть:

```text
обычный путь
↓
finally
```

и:

```text
exception
↓
catch
↓
finally
```

В обычных сценариях выполнения `finally` используется для кода, который должен выполняться после попытки выполнить операцию независимо от её результата.

---

# 20. `catch` и `finally` решают разные задачи

Это легко перепутать.

## `catch`

Отвечает:

> Что делать с возникшим исключением?

```java
catch (NumberFormatException e) {
    System.out.println("Некорректное число");
}
```

## `finally`

Отвечает:

> Что выполнить после попытки выполнить операцию?

```java
finally {
    System.out.println("Finish");
}
```

Сравнение:

```text
catch
→ обработка проблемы

finally
→ завершающее действие
```

Важно: `finally` сам по себе не считается обработкой исключения.

Например, если подходящего `catch` нет:

```text
try
↓
exception
↓
подходящего catch нет
↓
finally
↓
исключение продолжает
распространяться выше
```

То есть `finally` выполняет завершающий код, но необработанное исключение после этого остаётся исключением.

# 21. Зачем закрывать ресурсы

Некоторые объекты представляют внешние ресурсы:

```text
файл
соединение
поток ввода-вывода
```

С такими объектами часто есть жизненный цикл:

```text
открыли ресурс
↓
используем
↓
закрыли ресурс
```

Почему закрытие важно?

Потому что ресурс может занимать:

- системный дескриптор;
- соединение;
- память;
- другие ограниченные возможности операционной системы.

Проблема возникает, если между открытием и закрытием произошло исключение:

```text
открыли
↓
работаем
↓
exception
↓
до close() не дошли
```

Именно здесь становится особенно полезна конструкция try-with-resources.

---

# 22. Try-with-resources

Try-with-resources — специальная форма `try`, которая автоматически закрывает ресурс после использования.

Общая форма:

```java
try (SomeResource resource =
             new SomeResource()) {

    // работа с resource
}
```

Идея:

```text
создали ресурс
↓
работаем
↓
обычное завершение
или exception
↓
Java закрывает ресурс
```

То есть программисту не нужно вручную помнить о:

```java
resource.close();
```

в каждом пути выполнения.

### Главное

> Try-with-resources нужен не для обработки исключений, а для гарантированного закрытия подходящих ресурсов.

Практические примеры с настоящими файлами и потоками появятся на неделе 7.

---

# 23. Почему Java знает, как закрывать ресурс

Try-with-resources работает не с любым объектом.

Ресурс должен поддерживать общий контракт `AutoCloseable`.

Упрощённо интерфейс выглядит так:

```java
public interface AutoCloseable {
    void close() throws Exception;
}
```

То есть объект говорит:

```text
я поддерживаю AutoCloseable
↓
у меня есть close()
↓
меня можно автоматически закрыть
```

Сделаем простой учебный ресурс:

```java
public class MyResource
        implements AutoCloseable {

    public void work() {
        System.out.println("Working");
    }

    @Override
    public void close() {
        System.out.println("Resource closed");
    }
}
```

Теперь:

```java
try (MyResource resource =
             new MyResource()) {

    resource.work();
}
```

выведет:

```text
Working
Resource closed
```

Почему?

Потому что:

```text
MyResource
→ implements AutoCloseable
→ имеет close()

try-with-resources
→ знает общий контракт
→ вызывает close()
```

Связь с предыдущими неделями очевидна:

```text
interface
→ общий контракт поведения

конкретный класс
→ implements

код работает через контракт
```

### Главное

> Автозакрытие — не магия: оно работает благодаря интерфейсу `AutoCloseable`.

---

# 24. Что происходит «под капотом»

Код:

```java
try (MyResource resource =
             new MyResource()) {

    resource.work();
}
```

по смыслу похож на:

```java
MyResource resource =
        new MyResource();

try {
    resource.work();

} finally {
    resource.close();
}
```

Упрощённая модель:

```text
создать ресурс
↓
try
↓
работать
↓
обычное завершение
или exception
↓
finally
↓
close()
```

Поэтому ресурс закрывается и при успехе:

```text
work()
↓
успех
↓
close()
```

и при ошибке:

```text
work()
↓
exception
↓
close()
↓
исключение продолжает
обрабатываться
```

Это именно **упрощённая модель**.

Реальный код, который генерирует компилятор, сложнее: Java должна корректно учитывать ситуацию, когда исключение возникло и в основном коде, и во время `close()`.

Подробно этот механизм сейчас не нужен.

Нужно запомнить главное:

```text
try-with-resources
+
AutoCloseable
↓
автоматический вызов close()
```

---

# 25. Типичные ошибки при работе с исключениями

## Пустой `catch`

```java
try {
    int value = Integer.parseInt(text);

} catch (NumberFormatException e) {
}
```

Что произойдёт:

```text
ошибка возникла
↓
catch сработал
↓
информация потеряна
↓
программа выглядит так,
будто всё нормально
```

Это усложняет поиск ошибок.

## Ловим слишком общий тип

```java
try {
    ...
} catch (Exception e) {
    System.out.println("Ошибка");
}
```

Иногда общий `catch` действительно нужен, но использовать его автоматически для всего — плохая привычка.

Проблемы:

- теряется смысл конкретной ошибки;
- в обработчик могут попасть разные ситуации;
- становится неясно, умеет ли код действительно корректно реагировать на каждую из них.

Если ожидается:

```text
NumberFormatException
```

лучше сначала рассмотреть обработку именно этого типа.

## Исключения вместо обычного `if`

Плохо строить обычный алгоритм на исключениях.

Если ситуация является обычной веткой программы, чаще стоит использовать:

```text
if
return
boolean
```

а не искусственно превращать каждое условие в `throw/catch`.

## `throws Exception` везде

```java
public void process() throws Exception {
    ...
}
```

может заставить код компилироваться, но сильно ухудшает контракт.

Сравните:

```java
public void register()
        throws RegistrationException {
    ...
}
```

Здесь вызывающему коду сразу понятнее, какая проблема возможна.

### Главное

> Хороший код с исключениями не скрывает проблему, а делает её происхождение и ожидаемую реакцию понятнее.

---

# 26. Общая модель исключений

Соберём весь механизм.

Операция начинает обычное выполнение:

```text
операция
↓
обычный код
```

Возникает проблема:

```text
операция
↓
проблема
↓
exception
```

Исключение может возникнуть:

- внутри Java API;
- внутри стороннего кода;
- через наш `throw`.

После возникновения:

```text
исключение
↓
ищем подходящий catch
```

Если нашли:

```text
catch
↓
обработка
↓
возможное продолжение программы
```

Если не нашли:

```text
catch нет
↓
текущий метод прекращает обычную работу
↓
исключение передаётся вызывающему методу
↓
поиск продолжается выше
```

Checked-исключение дополнительно требует:

```text
catch
или
throws
```

А для ресурсов:

```text
AutoCloseable
+
try-with-resources
↓
автоматический close()
```

# 27. Что нужно решать для каждой ошибки

Когда в программе появляется потенциальная проблема, полезно пройти несколько вопросов.

## 1. Где проблема обнаруживается?

Например:

```text
Integer.parseInt(...)
→ понимает, что строка не число
```

## 2. Какой тип проблемы это описывает?

```text
NumberFormatException
```

или собственный:

```text
RegistrationException
```

## 3. Нужно ли использовать исключение вообще?

```text
обычный ожидаемый исход?
→ return / boolean / if

операция не может продолжиться?
→ exception
```

## 4. Кто знает, как правильно реагировать?

Не обязательно метод, где исключение возникло.

```text
низкий уровень
→ обнаружил проблему

верхний уровень
→ понимает сценарий
→ catch
```

## 5. Checked или unchecked?

Для checked вызывающий код обязан выбрать:

```text
catch
или
throws
```

## 6. Есть ли ресурс, который нужно закрыть?

Если объект реализует:

```text
AutoCloseable
```

стоит использовать:

```text
try-with-resources
```
