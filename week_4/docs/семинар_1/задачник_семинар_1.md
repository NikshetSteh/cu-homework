# Задача 1. Заказ контролирует своё состояние

**Обязательная**

**Ориентировочное время:** 15 минут

Начни с класса `Order`.

Заказ хранит:

```text
productName
unitPrice
quantity
completed
```

Все поля должны быть `private`.

При создании заказа через конструктор передаются:

```java
new Order("Keyboard", 2000, 2);
```

Добавь публичные операции:

```java
int getTotal()
boolean isCompleted()
boolean complete()
```

`getTotal()` возвращает полную стоимость заказа.

`complete()` завершает заказ и возвращает `true`, если операция выполнена.

## Правила

Заказ должен всегда оставаться в корректном состоянии:

```text
unitPrice > 0
quantity > 0
```

Завершённый заказ нельзя завершить второй раз.

## Пример 1

```text
Входные данные:
productName = "Keyboard"
unitPrice = 2000
quantity = 2

Действие:
complete()

Результат:
Стоимость: 4000
Заказ завершён: true
```

## Пример 2

```text
Действия:
complete()
complete()

Результат:
Первый вызов: true
Второй вызов: false
```

После этой задачи программа состоит практически из одного класса.

# Задача 2. Выносим работу со складом

**Обязательная**

**Ориентировочное время:** 15 минут

Теперь заказ нельзя завершить, если товара нет на складе.

Не добавляй поле:

```java
int stock;
```

в `Order`.

Вместо этого создай отдельный класс:

```text
InventoryItem
```

Он хранит:

```text
productName
availableQuantity
```

и сам контролирует остаток.

Добавь операции:

```java
boolean hasEnough(int amount)
boolean take(int amount)
int getAvailableQuantity()
```

Теперь `Order` должен содержать объект:

```java
InventoryItem item;
```

а не только название товара.

## Новая модель

```text
Order
└── InventoryItem
```

При завершении заказа нужно убедиться, что нужное количество товара существует.

Если товара недостаточно, заказ не завершается и остаток не меняется.

## Пример 1

```text
Склад:
Keyboard — 10

Заказ:
Keyboard × 3

Действие:
complete()

Результат:
Заказ завершён: true
Остаток: 7
```

## Пример 2

```text
Склад:
Keyboard — 2

Заказ:
Keyboard × 3

Действие:
complete()

Результат:
Заказ завершён: false
Остаток: 2
```

## После решения

Сравни две версии программы:

```text
до:
Order знает всё

после:
Order отвечает за заказ
InventoryItem отвечает за остаток
```

# Задача 3. Выносим сценарий в `OrderService`

**Обязательная**

**Ориентировочное время:** 15 минут

Сейчас `Order.complete()` начинает делать слишком много:

```text
проверяет склад
↓
уменьшает остаток
↓
изменяет состояние заказа
```

Переработай программу.

Сам `Order` должен отвечать только за собственное состояние.

`InventoryItem` — только за складской остаток.

Создай:

```java
class OrderService
```

с методом:

```java
boolean complete(Order order)
```

Именно `OrderService` должен координировать сценарий:

```text
проверить возможность выполнения
↓
попросить InventoryItem выдать товар
↓
попросить Order перейти в completed
```

При этом он не должен напрямую менять `private`-поля других объектов.

## Пример 1

```text
Склад:
Keyboard — 5

Заказ:
Keyboard × 2

Действие:
service.complete(order)

Результат:
true

Заказ завершён: true
Остаток товара: 3
```

## Пример 2

```text
Склад:
Keyboard — 1

Заказ:
Keyboard × 2

Действие:
service.complete(order)

Результат:
false

Заказ завершён: false
Остаток товара: 1
```

## Основной вопрос

После решения для каждого класса сформулируй **одним предложением его ответственность**.

# Задача 4. Добавляем оплату через контракт

**Обязательная**

**Ориентировочное время:** 17 минут

Теперь заказ нужно сначала оплатить.

Есть два способа оплаты:

```text
банковская карта
бонусы
```

Не добавляй в `OrderService`:

```java
if (paymentType.equals("card")) {
    ...
} else if (paymentType.equals("bonus")) {
    ...
}
```

Вместо этого создай контракт:

```java
interface PaymentProcessor {
    boolean pay(int amount);
}
```

И две реализации:

```text
CardPaymentProcessor
BonusPaymentProcessor
```

## `CardPaymentProcessor`

Хранит баланс карты.

Оплата проходит, если денег достаточно.

## `BonusPaymentProcessor`

Хранит количество бонусов.

Один бонус равен одному рублю.

`OrderService` должен получать `PaymentProcessor` через конструктор:

```java
OrderService(PaymentProcessor paymentProcessor)
```

Новый сценарий:

```text
проверить товар
↓
выполнить оплату
↓
уменьшить остаток
↓
завершить заказ
```

## Пример 1

```text
Заказ:
total = 4000

Карта:
balance = 5000

Склад:
quantity = 10

Результат:
Заказ завершён: true
Баланс карты: 1000
Остаток товара: 8
```

## Пример 2

```text
Заказ:
total = 4000

Бонусы:
2500

Склад:
quantity = 10

Результат:
Заказ завершён: false
Бонусы: 2500
Остаток товара: 10
```

## Проверка архитектуры

Замена:

```java
new CardPaymentProcessor(...)
```

на:

```java
new BonusPaymentProcessor(...)
```

не должна требовать изменения кода `OrderService`.

# Задача 5. Добавляем уведомления и собираем систему

**Обязательная**

**Ориентировочное время:** 18 минут

После успешного завершения заказа пользователь должен получить сообщение.

Создай:

```java
interface MessageSender {
    void send(String message);
}
```

и реализации:

```text
ConsoleSender
EmailSender
```

Реальную отправку email реализовывать не нужно.

Например:

```text
Email: Order completed
```

`OrderService` теперь должен зависеть от двух контрактов:

```java
PaymentProcessor
MessageSender
```

Конструктор:

```java
OrderService(
    PaymentProcessor paymentProcessor,
    MessageSender messageSender
)
```

Полный сценарий:

```text
проверить доступность товара
↓
попытаться оплатить
↓
списать товар
↓
завершить заказ
↓
отправить уведомление
```

Сообщение отправляется **только после успешного завершения заказа**.

## Пример 1

```text
Склад:
Keyboard — 10

Заказ:
Keyboard × 2
total = 4000

PaymentProcessor:
CardPaymentProcessor(5000)

MessageSender:
EmailSender

Результат:
Заказ завершён: true
Остаток товара: 8
Баланс карты: 1000

Email: Order completed
```

## Пример 2

```text
Склад:
Keyboard — 1

Заказ:
Keyboard × 2
total = 4000

Результат:
Заказ завершён: false
Остаток товара: 1
Сообщение не отправлено
```

## Финальная структура

К концу обязательной части должна получиться примерно такая система:

```text
                  PaymentProcessor
                  ▲              ▲
                  │              │
        CardPaymentProcessor   BonusPaymentProcessor


                    MessageSender
                    ▲           ▲
                    │           │
               EmailSender   ConsoleSender


          PaymentProcessor   MessageSender
                 ▲                ▲
                 │                │
                 └──── OrderService ────> Order
                                          │
                                          ▼
                                    InventoryItem
```

При этом:

```text
Order
→ отвечает за состояние заказа

InventoryItem
→ отвечает за остаток товара

PaymentProcessor
→ контракт оплаты

MessageSender
→ контракт уведомления

OrderService
→ координирует сценарий
```

## Дополнительная часть — рефакторинг сервиса аренды самокатов

**Дополнительная**

**Ориентировочное время:** ~80 минут

Перед тобой первая версия небольшого приложения для аренды электросамокатов.

Программа умеет:

- найти самокат по идентификатору;
- проверить его доступность;
- проверить заряд;
- рассчитать стоимость аренды;
- списать деньги;
- изменить состояние самоката;
- отправить пользователю сообщение.

Программа работает, но её написали очень быстро перед демонстрацией инвесторам.

Теперь код нужно подготовить к развитию продукта.

---

# Исходный код

```java
public class Main {

    public static void main(String[] args) {
        AppData data = new AppData();

        // Запрос пользователя
        String scooterId = "S-102";
        int minutes = 35;
        int userBalance = 500;

        String tariff = "student";
        String notificationType = "console";

        // Ищем самокат
        int scooterIndex = -1;

        for (int i = 0; i < data.scooterIds.length; i++) {
            if (data.scooterIds[i].equals(scooterId)) {
                scooterIndex = i;
                break;
            }
        }

        if (scooterIndex == -1) {
            System.out.println("Scooter not found");
            return;
        }

        // Проверяем доступность
        if (!data.available[scooterIndex]) {
            System.out.println("Scooter is not available");
            return;
        }

        // Проверяем длительность
        if (minutes < 10 || minutes > 120) {
            System.out.println("Invalid rental duration");
            return;
        }

        // На каждые начатые 2 минуты требуется 1% заряда
        int requiredBattery = (minutes + 1) / 2;

        if (data.battery[scooterIndex] < requiredBattery) {
            System.out.println("Not enough battery");
            return;
        }

        // Считаем стоимость
        int pricePerMinute;

        if (tariff.equals("standard")) {
            pricePerMinute = 10;
        } else if (tariff.equals("student")) {
            pricePerMinute = 8;
        } else {
            System.out.println("Unknown tariff");
            return;
        }

        int price = minutes * pricePerMinute;

        // Проверяем деньги
        if (userBalance < price) {
            System.out.println("Not enough money");
            return;
        }

        // Меняем состояние
        userBalance -= price;

        data.available[scooterIndex] = false;
        data.battery[scooterIndex] -= requiredBattery;

        System.out.println("Rental started");
        System.out.println("Scooter: " + data.scooterIds[scooterIndex]);
        System.out.println("Price: " + price);
        System.out.println("Balance: " + userBalance);
        System.out.println(
                "Battery: " + data.battery[scooterIndex]
        );

        // Отправляем уведомление
        if (notificationType.equals("console")) {
            System.out.println(
                    "Notification: rental started for " + scooterId
            );
        } else if (notificationType.equals("email")) {
            System.out.println(
                    "Email: rental started for " + scooterId
            );
        }
    }
}


class AppData {

    public String[] scooterIds = {
            "S-101",
            "S-102",
            "S-103"
    };

    public int[] battery = {
            80,
            35,
            90
    };

    public boolean[] available = {
            true,
            true,
            false
    };
}
```

# Этап 1. Разберитесь, что с этим кодом не так

**Ориентировочное время:** 10 минут

Пока не переписывай программу.

Найди в ней разные ответственности.

Ответь:

- кто сейчас отвечает за поиск самоката;
- кто отвечает за правила состояния самоката;
- кто рассчитывает стоимость;
- кто проводит оплату;
- кто отправляет уведомление;
- кто хранит данные;
- кто координирует весь сценарий.

Обрати внимание на массивы:

```java
data.scooterIds[i]
data.battery[i]
data.available[i]
```

Что произойдёт, если данные случайно окажутся несинхронизированы?

Например:

```text
scooterIds[1]
battery[1]
available[1]
```

должны всегда описывать один самокат.

Также подумай, какие строки можно изменить извне так, что состояние приложения станет некорректным:

```java
data.battery[0] = -100;
data.available[0] = false;
```

# Этап 2. Разделите данные и бизнес-логику

**Ориентировочное время:** 25 минут

Переработай программу так, чтобы состояние одного самоката больше не хранилось в нескольких параллельных массивах.

Каждый самокат должен сам контролировать своё состояние.

Для него должны выполняться правила:

```text
0 <= battery <= 100
```

Недоступный самокат нельзя арендовать повторно.

Нельзя потратить больше заряда, чем есть.

Внешний код не должен иметь возможности написать:

```java
scooter.battery = -500;
```

или каким-либо аналогичным способом сломать состояние объекта.

При этом данные о нескольких самокатах по-прежнему можно хранить **в обычном массиве**.

## Важное архитектурное требование

Код, выполняющий сценарий аренды, не должен самостоятельно:

```text
перебирать массив
↓
сравнивать id
↓
работать с индексами
```

Он должен попросить объект, отвечающий за хранение самокатов:

> Найди мне самокат с таким id.

Как именно внутри выполняется поиск — деталь хранения.

## После рефакторинга

`main` не должен содержать всю бизнес-логику.

Он должен выглядеть примерно по смыслу так:

```text
создать объекты приложения
↓
создать запрос на аренду
↓
попросить приложение выполнить аренду
↓
вывести результат
```

Конкретные классы и сигнатуры придумай самостоятельно.

# Этап 3. Бизнес добавляет новый тариф

**Ориентировочное время:** 20 минут

Сейчас стоимость рассчитывается так:

```text
standard → 10 рублей / минута
student  → 8 рублей / минута
```

Появился новый тариф:

```text
evening
```

Его правила:

- первые `30` минут стоят `12` рублей за минуту;
- всё время сверх `30` минут стоит `6` рублей за минуту.

Например:

```text
20 минут
→ 240 рублей
```

```text
50 минут
→ 30 × 12 + 20 × 6
→ 480 рублей
```

Есть важное требование бизнеса:

> В будущем тарифы будут появляться регулярно.

Добавление тарифа не должно требовать изменения основной логики аренды.

То есть вариант:

```java
if (tariff.equals("standard")) {
    ...
} else if (tariff.equals("student")) {
    ...
} else if (tariff.equals("evening")) {
    ...
}
```

в коде, который запускает аренду, больше не подходит.

## Задача

Переработай дизайн так, чтобы логика аренды знала только:

> Мне нужен объект, который умеет рассчитать стоимость поездки.

Как именно стоимость рассчитывается — её не интересует.

Самостоятельно реши:

- нужен ли здесь отдельный контракт;
- какие реализации нужны;
- какой объект должен получать эту зависимость.

## Проверка

После рефакторинга должна быть возможна замена:

```text
standard
```

на:

```text
student
```

или:

```text
evening
```

без изменения основной логики аренды.

# Этап 4. Меняем уведомления

**Ориентировочное время:** 15 минут

Сейчас в исходной программе есть:

```java
if (notificationType.equals("console")) {
    ...
} else if (notificationType.equals("email")) {
    ...
}
```

Через неделю команда планирует добавить:

```text
SMS
```

У приложения появляется новое требование:

> Сценарий аренды должен уметь отправить сообщение, но не должен знать, куда именно оно отправляется.

Переработай эту часть.

## Требование

Добавление нового способа уведомления не должно требовать изменения кода, отвечающего за:

- поиск самоката;
- проверку аренды;
- расчёт стоимости;
- изменение состояния самоката;
- оплату.

# Этап 5. Проверьте получившийся дизайн

**Ориентировочное время:** 10 минут

После рефакторинга ответь для каждого своего класса:

```text
За что отвечает этот класс?
```

Если ответ выглядит так:

> Он ищет самокаты, считает стоимость, списывает деньги, отправляет сообщения и ещё выводит информацию,

скорее всего, ответственности всё ещё смешаны.

Проверь следующие требования.

## Состояние

Нельзя напрямую сделать:

```text
battery = -100
```

или другим способом нарушить состояние самоката.

## Хранение

Код бизнес-логики не знает:

```text
в каком индексе массива находится самокат
```

и не работает с массивом напрямую.

## Тариф

Чтобы добавить ещё один тариф, не нужно изменять основную логику аренды.

## Уведомления

Чтобы добавить ещё один способ отправки сообщения, не нужно изменять основную логику аренды.

## `main`

`main` не содержит большой последовательности:

```text
поиск
↓
проверки
↓
if тарифа
↓
изменение массивов
↓
if уведомления
```

Он в основном создаёт и связывает объекты, запускает сценарий и показывает результат.
