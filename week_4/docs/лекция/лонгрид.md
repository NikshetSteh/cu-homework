# Java 1. Неделя 4 — ООП: инкапсуляция, композиция и интерфейсы

## Зачем нужна эта неделя

На прошлой неделе мы научились создавать собственные классы и объекты. Мы уже умеем описывать состояние объекта полями, поведение — методами, создавать конструкторы и работать со ссылками.

Теперь возникает следующий вопрос:

> Что делать, когда программа состоит не из одного класса, а из нескольких взаимодействующих объектов?

Сам факт наличия классов ещё не делает программу хорошо спроектированной. Можно создать один огромный класс с десятками полей и методов, открыть все данные наружу и связать классы так, что любое изменение потребует переписывать половину программы.

На этой неделе мы сделаем следующий шаг:

```text
отдельный класс
↓
объект контролирует своё состояние
↓
у класса появляется понятная ответственность
↓
объекты начинают взаимодействовать
↓
для взаимодействия используются небольшие контракты
```

Мы разберём:

- инкапсуляцию;
- инварианты объекта;
- публичный интерфейс класса;
- ответственность класса;
- композицию;
- делегирование;
- Java-интерфейсы;
- зависимость от контракта, а не от конкретной реализации.

Полноценное наследование и полиморфизм будут на следующей неделе. Здесь мы подойдём к ним только настолько, насколько это нужно для понимания интерфейсов.

# 1. От класса к объектно-ориентированной программе

Начнём с уже знакомого класса.

```java
class BankAccount {
    String owner;
    int balance;

    void deposit(int amount) {
        balance += amount;
    }
}
```

У объекта есть:

```text
состояние
→ owner, balance

поведение
→ deposit(...)
```

Эта модель нам уже знакома:

```text
объект
=
состояние + поведение
```

Но у такого класса есть проблема. Поля доступны снаружи напрямую:

```java
BankAccount account = new BankAccount();

account.balance = 1000;
account.balance = -5000;
```

Метод `deposit()` может содержать сколько угодно проверок, но внешний код всё равно может обойти их и записать в поле любое значение.

Получается:

```text
объект хранит состояние
↓
но не контролирует его
```

Если у банковского счёта есть правило «баланс не может быть отрицательным», класс пока никак не может гарантировать это правило.

Именно отсюда возникает первая идея недели — **инкапсуляция**.

---

# 2. Инкапсуляция: объект контролирует своё состояние

## Проблема прямого доступа

Представим, что баланс счёта можно менять напрямую:

```java
account.balance = 500;
account.balance = -1000;
account.balance = 1_000_000;
```

С точки зрения синтаксиса Java все эти операции допустимы.

Но с точки зрения предметной задачи некоторые значения могут быть запрещены.

Значит, между внешним кодом и состоянием объекта нужен контролируемый путь:

```text
внешний код
↓
допустимая операция
↓
проверка правил
↓
изменение состояния
```

## Скрываем состояние

Для этого поля обычно делают `private`:

```java
class BankAccount {
    private int balance;
}
```

Теперь внешний код не может обратиться к полю напрямую:

```java
BankAccount account = new BankAccount();

account.balance = -5000; // ошибка компиляции
```

Это уже лучше: состояние скрыто.

Но просто написать `private` недостаточно. Нужно ещё предоставить осмысленные операции, через которые объект можно изменять.

```java
class BankAccount {
    private int balance;

    public void deposit(int amount) {
        if (amount > 0) {
            balance += amount;
        }
    }

    public int getBalance() {
        return balance;
    }
}
```

Теперь внешний код работает так:

```java
BankAccount account = new BankAccount();

account.deposit(500);

System.out.println(account.getBalance());
```

Изменение происходит не напрямую, а через метод:

```text
account.deposit(500)
↓
проверка amount > 0
↓
изменение balance
```

## Что такое инкапсуляция

> **Инкапсуляция** — объект контролирует доступ к своему состоянию и предоставляет допустимые операции для работы с ним.

То есть важны сразу две части:

```text
скрыть детали
+
дать понятный способ работы
```

Только скрыть поле — недостаточно.

## Инкапсуляция — не «private + getters/setters»

Частая ошибка — запомнить инкапсуляцию как механическое правило:

```text
все поля private
+
для каждого поля getter
+
для каждого поля setter
```

Например:

```java
class BankAccount {
    private int balance;

    public void setBalance(int balance) {
        this.balance = balance;
    }

    public int getBalance() {
        return balance;
    }
}
```

Внешний код снова может сделать:

```java
account.setBalance(-5000);
```

Формально поле `private`, но объект всё ещё позволяет записать недопустимое состояние.

Поэтому полезнее думать не так:

```text
какой setter нужен полю?
```

а так:

```text
какие операции имеет смысл разрешить объекту?
```

Для банковского счёта:

```java
account.deposit(500);
```

обычно выражает смысл задачи лучше, чем:

```java
account.setBalance(500);
```

Первая команда говорит «внести 500 на счёт», вторая — «заменить баланс числом 500». Это разные действия.

### Главное

```text
инкапсуляция
≠
автоматическая генерация getters/setters

инкапсуляция
=
контроль состояния через осмысленные операции
```

# 3. Инвариант объекта

Когда объект начинает контролировать своё состояние, появляется следующий вопрос:

> Как понять, какое состояние объекта считается корректным?

Допустим, для нашего учебного банковского счёта действует правило:

```text
balance >= 0
```

Если объект корректен, это условие должно выполняться.

Такое условие называют **инвариантом объекта**.

> **Инвариант** — условие, которое должно оставаться истинным для корректного объекта.

Для `BankAccount`:

```text
инвариант:
balance >= 0
```

## Сохраняем инвариант

```java
class BankAccount {
    private int balance;

    public void deposit(int amount) {
        if (amount > 0) {
            balance += amount;
        }
    }

    public void withdraw(int amount) {
        if (amount > 0 && amount <= balance) {
            balance -= amount;
        }
    }

    public int getBalance() {
        return balance;
    }
}
```

Если на счёте 500 и мы вызываем:

```java
account.withdraw(200);
```

получаем:

```text
balance = 500
amount = 200
↓
amount > 0
→ true
↓
amount <= balance
→ true
↓
balance = 300
```

Инвариант сохранился.

Если попытаться снять 700:

```text
balance = 500
amount = 700
↓
amount <= balance
→ false
↓
balance не меняется
```

Инвариант снова сохранился.

## Почему проверка должна быть внутри объекта

Можно было бы писать проверки снаружи:

```java
if (amount <= account.getBalance()) {
    account.withdraw(amount);
}
```

Но тогда каждый пользователь класса должен помнить правила счёта.

```text
правило относится к BankAccount
↓
значит BankAccount и должен его защищать
```

Если правило разбросано по внешнему коду, легко забыть одну проверку.

## Важное ограничение

На этой неделе мы не обсуждаем подробно, что делать, если операция невозможна: молча ничего не делать, возвращать `boolean`, выбрасывать исключение и т. д.

Механизм исключений будет отдельной темой позже.

Сейчас важнее сама идея:

```text
объект
↓
знает свои правила
↓
не позволяет публичным операциям разрушать корректное состояние
```

### Главное

```text
private состояние
+
контролируемые public-методы
↓
можно поддерживать инвариант
```

# 4. Публичный интерфейс класса

Посмотрим на простой класс:

```java
class Counter {
    private int value;

    public void increment() {
        value++;
    }

    public int getValue() {
        return value;
    }
}
```

Внешний код:

```java
Counter counter = new Counter();

counter.increment();
counter.increment();

System.out.println(counter.getValue());
```

Пользователю класса достаточно знать:

```text
increment()
getValue()
```

Как именно внутри хранится значение — отдельная деталь.

```text
публичная часть
----------------
increment()
getValue()

внутренняя часть
----------------
private int value
```

Публичную часть можно назвать **публичным интерфейсом класса**.

> Публичный интерфейс класса — набор операций, которыми внешний код может пользоваться.

Здесь слово «интерфейс» используется в обычном смысле: способ взаимодействия с объектом.

Позже появится специальная конструкция Java:

```java
interface MessageSender {
    void send(String message);
}
```

Важно различать:

```text
публичный интерфейс класса
→ доступные снаружи операции

Java interface
→ отдельная конструкция языка
```

## Публичный контракт и реализация

Полезно отделять:

```text
контракт
→ что объект позволяет делать

реализация
→ как именно объект это делает
```

Например, пользователь `Counter` знает:

```java
counter.increment();
```

Ему не нужно знать, как именно внутри хранится счётчик.

### Главное

> Пользователь класса должен зависеть прежде всего от его публичного поведения, а не от внутренних деталей.

# 5. Ответственность класса

До этого момента мы обсуждали отдельный объект.

Теперь представим класс заказа:

```java
class Order {
    void calculateTotal() {
        // ...
    }

    void printReceipt() {
        // ...
    }

    void saveToFile() {
        // ...
    }

    void sendEmail() {
        // ...
    }
}
```

На первый взгляд всё удобно: вся логика заказа находится в одном месте.

Но со временем класс может превратиться в список несвязанных задач:

```text
Order
├── считает стоимость
├── хранит состояние
├── печатает чек
├── сохраняет файл
├── отправляет email
└── занимается ещё десятком вещей
```

Возникает вопрос:

> За какую часть программы вообще отвечает `Order`?

## Понятная зона ответственности

Хороший класс обычно имеет понятную ответственность.

Например:

```text
Order
→ состояние и правила заказа

ReceiptPrinter
→ печать чека

EmailSender
→ отправка сообщения
```

На этой неделе нам не нужен формальный архитектурный принцип с названием и аббревиатурой.

Достаточно простой проверки:

> Могу ли я одним коротким предложением объяснить, за что отвечает этот класс?

Например:

```text
BankAccount
→ управляет состоянием банковского счёта

Order
→ хранит состояние заказа и операции над ним

EmailSender
→ отправляет сообщения по email
```

Если описание превращается в длинное перечисление несвязанных действий, скорее всего, в классе смешаны разные ответственности.

## Связность внутри класса

Поля и методы класса должны быть связаны общей задачей.

```java
class BankAccount {
    private int balance;

    public void deposit(int amount) {
        // ...
    }

    public void withdraw(int amount) {
        // ...
    }

    public int getBalance() {
        return balance;
    }
}
```

Все элементы относятся к одной сущности — банковскому счёту.

А такой метод выглядел бы подозрительно:

```java
public void printWeatherForecast() {
    // ...
}
```

Он никак не связан с задачей банковского счёта.

Удобная модель:

```text
внутри класса
↓
связанные данные
+
связанное поведение
```

### Главное

> Класс должен иметь понятную ответственность, а его поля и методы — относиться к этой ответственности.

# 6. От одного большого класса к нескольким объектам

Если один класс не должен делать всё, программу нужно разделить.

Например:

```text
заказ
+
отправка уведомления
```

Можно представить двумя объектами:

```text
Order
→ отвечает за заказ

EmailSender
→ отвечает за отправку email
```

Но тогда появляется новая задача:

> Как этим объектам взаимодействовать?

Один объект может хранить ссылку на другой объект в поле.

Это уже знакомый механизм: мы использовали поля и раньше. Просто теперь значение поля — другой объект.

Например:

```java
class Engine {
    public void start() {
        System.out.println("Engine started");
    }
}
```

И класс автомобиля:

```java
class Car {
    private Engine engine;

    public Car(Engine engine) {
        this.engine = engine;
    }
}
```

Создание:

```java
Engine engine = new Engine();
Car car = new Car(engine);
```

Схема:

```text
car
↓
Car
│
└── engine ──→ Engine
```

# 7. Композиция

Когда один объект включает другой объект как часть своей структуры, мы получаем композицию.

Для нашей рабочей модели достаточно:

> **Композиция** — способ строить объект из других объектов.

Пример:

```text
Car
│
└── Engine
```

или:

```text
Order
│
└── Customer
```

В Java это часто выглядит как обычное поле:

```java
class Car {
    private Engine engine;
}
```

Нового специального ключевого слова для композиции нет.

Мы используем уже знакомую возможность языка:

```text
поле
↓
может хранить ссылку на другой объект
```

## Почему композиция полезна

Допустим, `Car` должен запускать двигатель.

Можно было бы поместить всю логику двигателя внутрь `Car`.

Но если `Engine` — самостоятельная часть системы, удобнее дать ему собственную ответственность:

```java
class Engine {
    public void start() {
        System.out.println("Engine started");
    }
}
```

А `Car` хранит двигатель:

```java
class Car {
    private Engine engine;

    public Car(Engine engine) {
        this.engine = engine;
    }
}
```

Теперь два класса отвечают за разные вещи:

```text
Car
→ автомобиль

Engine
→ двигатель
```

## Не углубляемся в терминологию

В более подробных курсах различают композицию и агрегацию, обсуждают жизненный цикл частей объекта и формальные UML-связи.

Сейчас это не наша цель.

Для недели 4 достаточно модели:

```text
один объект
↓
хранит ссылку на другой объект
↓
использует его как часть своей работы
```

### Главное

```text
сложный объект
↓
можно собрать
из нескольких более простых объектов
```

# 8. Делегирование

Композиция отвечает на вопрос:

> Какие объекты связаны?

Но остаётся другой вопрос:

> Кто именно выполняет работу?

Добавим в `Car` метод `start()`:

```java
class Engine {
    public void start() {
        System.out.println("Engine started");
    }
}

class Car {
    private Engine engine;

    public Car(Engine engine) {
        this.engine = engine;
    }

    public void start() {
        engine.start();
    }
}
```

При вызове:

```java
car.start();
```

происходит:

```text
car.start()
↓
Car получает запрос
↓
Car вызывает engine.start()
↓
Engine выполняет свою работу
```

`Car` не копирует внутрь себя реализацию двигателя. Он передаёт задачу объекту, который за неё отвечает.

Это называется **делегированием**.

> Делегирование — объект передаёт часть работы другому объекту.

## Композиция и делегирование

Эти идеи часто идут вместе, но означают разное.

| Идея | Главный вопрос | Пример |
| --- | --- | --- |
| композиция | кто с кем связан? | `Car` содержит `Engine` |
| делегирование | кто кому передаёт работу? | `Car.start()` вызывает `engine.start()` |

То есть:

```java
private Engine engine;
```

показывает связь объектов, а:

```java
engine.start();
```

передаёт выполнение другому объекту.

## Связь с ответственностью

Мы получили естественную цепочку:

```text
класс не должен делать всё сам
↓
часть работы относится к другому объекту
↓
объекты связываем
↓
композиция
↓
работу передаём нужному объекту
↓
делегирование
```

### Главное

> Хороший объект не обязан самостоятельно выполнять каждую операцию. Он может координировать работу других объектов.

# 9. Проблема зависимости от конкретной реализации

Рассмотрим другой пример.

Есть класс для отправки email:

```java
class EmailSender {
    public void send(String message) {
        System.out.println("Email: " + message);
    }
}
```

И сервис оформления заказа:

```java
class OrderService {
    private EmailSender sender;

    public OrderService(EmailSender sender) {
        this.sender = sender;
    }

    public void completeOrder() {
        sender.send("Order completed");
    }
}
```

Сейчас зависимость выглядит так:

```text
OrderService
↓
EmailSender
```

Для текущей задачи это работает.

Но представим, что появились другие способы уведомления:

```text
Email
SMS
Push
Console
```

Нужно ли `OrderService` знать, какой именно способ используется?

Посмотрим на его код:

```java
sender.send("Order completed");
```

`OrderService` фактически требуется только одно:

```text
объект умеет
send(String message)
```

Ему не обязательно знать конкретный класс.

Возникает новая потребность:

> Как описать требуемое поведение отдельно от конкретной реализации?

Для этого в Java есть `interface`.

---

# 10. `interface` как контракт поведения

Создадим интерфейс:

```java
interface MessageSender {
    void send(String message);
}
```

На этом этапе полезно читать его почти как текст:

```text
MessageSender
↓
любой объект этой роли
должен уметь
↓
send(String message)
```

Интерфейс говорит, **что должно быть доступно**, но не говорит, **как именно это сделать**.

Например, интерфейс не выбирает:

```text
отправить email?
вывести в консоль?
отправить SMS?
```

Он задаёт общий контракт:

```text
можно отправить сообщение
```

## Реализация интерфейса

Класс может указать, что он реализует интерфейс:

```java
class EmailSender implements MessageSender {

    public void send(String message) {
        System.out.println("Email: " + message);
    }
}
```

Ключевое слово:

```java
implements
```

можно читать так:

```text
EmailSender
реализует контракт
MessageSender
```

Если класс объявил `implements MessageSender`, он должен предоставить требуемое поведение `send(...)`.

## Вторая реализация

```java
class ConsoleSender implements MessageSender {

    public void send(String message) {
        System.out.println(message);
    }
}
```

Теперь:

```text
MessageSender
├── EmailSender
└── ConsoleSender
```

Оба класса выполняют одну роль, но делают работу по-разному.

Для интерфейса важен не способ реализации, а наличие операции:

```java
send(String message)
```

## Интерфейс — не «класс без полей»

Не стоит запоминать интерфейс как:

```text
обычный класс,
только без состояния
```

На этой неделе лучше использовать более полезное определение:

> **Интерфейс описывает роль или контракт поведения.**

Например:

```text
MessageSender
→ умеет отправлять сообщение
```

Позже мы увидим больше возможностей интерфейсов, но сейчас они не нужны.

Мы сознательно не разбираем:

- `default`-методы;
- `static`-методы интерфейсов;
- `private`-методы интерфейсов;
- сложные комбинации интерфейсов.

### Главное

```text
interface
↓
описывает требуемое поведение

class ... implements ...
↓
предоставляет конкретную реализацию
```

# 11. Интерфейс как тип зависимости

Теперь изменим `OrderService`.

Было:

```java
class OrderService {
    private EmailSender sender;

    public OrderService(EmailSender sender) {
        this.sender = sender;
    }
}
```

Здесь `OrderService` требует конкретный `EmailSender`.

Но ему нужен только объект, который умеет `send(...)`.

Поэтому поле можно объявить через интерфейс:

```java
class OrderService {
    private MessageSender sender;

    public OrderService(MessageSender sender) {
        this.sender = sender;
    }

    public void completeOrder() {
        sender.send("Order completed");
    }
}
```

Теперь зависимость выглядит так:

```text
OrderService
↓
MessageSender
```

## Передаём `EmailSender`

```java
MessageSender sender = new EmailSender();

OrderService service = new OrderService(sender);

service.completeOrder();
```

Здесь переменная имеет тип:

```java
MessageSender
```

а объект создан как:

```java
new EmailSender()
```

Пока достаточно практической модели:

> Переменная интерфейсного типа может ссылаться на объект класса, который этот интерфейс реализует.

То есть:

```java
MessageSender sender = new EmailSender();
```

корректно, потому что `EmailSender implements MessageSender`.

## Меняем реализацию

Теперь вместо email используем консоль:

```java
MessageSender sender = new ConsoleSender();

OrderService service = new OrderService(sender);

service.completeOrder();
```

Сам `OrderService` менять не пришлось.

Это ключевой результат.

Было:

```text
OrderService
↓
конкретный EmailSender
```

Стало:

```text
OrderService
↓
контракт MessageSender
↓
конкретная реализация выбирается снаружи
```

`OrderService` знает только:

```java
sender.send(...);
```

И этого ему достаточно.

## Зачем это нужно

Сравним две модели.

### Зависимость от конкретного класса

```text
OrderService
↓
EmailSender
```

`OrderService` напрямую привязан к одному способу отправки.

### Зависимость от контракта

```text
              MessageSender
              /           \
             /             \
     EmailSender       ConsoleSender
             \             /
              \           /
               OrderService
```

`OrderService` работает с ролью `MessageSender`.

Ему не нужно знать внутреннее устройство каждой реализации.

### Главное

> Класс может требовать объект с нужным поведением, а не конкретный класс.

# 12. Что здесь уже похоже на полиморфизм

Посмотрим на два фрагмента:

```java
MessageSender sender = new EmailSender();
sender.send("Hello");
```

и:

```java
MessageSender sender = new ConsoleSender();
sender.send("Hello");
```

Переменная в обоих случаях имеет один тип:

```java
MessageSender
```

Но фактические объекты разные.

```text
MessageSender
↓
EmailSender

или

MessageSender
↓
ConsoleSender
```

Это уже подводит нас к полиморфизму.

Но подробный механизм будет темой следующей недели.

Пока достаточно запомнить:

```text
интерфейс
→ общий контракт

разные классы
→ разные реализации

переменная интерфейсного типа
→ может работать с любой такой реализацией
```

Мы пока не разбираем подробно:

- динамическое связывание;
- наследование классов;
- `extends`;
- `super`;
- абстрактные классы;
- приведение типов;
- `instanceof`.

# 13. Отношения «содержит» и «является»

Когда классов становится несколько, полезно проговаривать их отношения обычными словами.

## «Содержит»

Например:

```text
Car имеет Engine
```

Это естественно выражается полем:

```java
class Car {
    private Engine engine;
}
```

Рабочая модель:

```text
Car
содержит / использует
Engine
```

Это композиция.

## «Является»

Для интерфейса можно сказать:

```text
EmailSender является MessageSender
```

То есть `EmailSender` выполняет роль, заданную интерфейсом.

В Java:

```java
class EmailSender implements MessageSender {
    // ...
}
```

На этой неделе отношение «является» мы рассматриваем только через реализацию интерфейса.

Наследование классов через `extends` будет следующим большим шагом курса.

## Полезная проверка словами

Перед тем как связывать классы, попробуйте проговорить связь.

```text
Car имеет Engine
→ естественно
→ поле / композиция
```

```text
EmailSender является MessageSender
→ естественно
→ implements
```

Если фраза звучит странно, возможно, модель выбрана плохо.

### Главное

```text
«содержит»
→ обычно связь объектов через поле

«реализует роль»
→ interface + implements
```

# 14. Связанность между классами

Представим два варианта.

## Сильная зависимость от деталей

```text
OrderService
↓
знает конкретный EmailSender
↓
может начать зависеть
от деталей EmailSender
```

Если один класс знает слишком много о другом, изменение второго может потребовать изменений в первом.

## Небольшой контракт

```text
OrderService
↓
MessageSender
↓
знает только send(...)
```

Теперь `OrderService` знает меньше.

Это полезная общая идея:

> Чем меньше один класс знает о внутренних деталях другого, тем проще классы изменять независимо.

На более продвинутом уровне для этого существуют отдельные термины и метрики. Сейчас они не нужны.

Достаточно простой модели:

```text
между классами
↓
минимум лишнего знания
+
понятные операции взаимодействия
```

# 15. Две стороны хорошего разделения

Теперь можно собрать две идеи вместе.

## Внутри класса

Хочется, чтобы вместе находились связанные данные и поведение.

```text
BankAccount
├── balance
├── deposit(...)
├── withdraw(...)
└── getBalance()
```

## Между классами

Хочется, чтобы объекты знали друг о друге только необходимое.

```text
OrderService
↓
MessageSender
↓
send(...)
```

Не нужно знать, как именно сообщение отправляется.

Общая модель:

```text
внутри класса
→ связанные обязанности вместе

между классами
→ минимум лишних зависимостей
```

# 16. Составной пример: оформление заказа

Теперь соберём основные идеи недели в одном небольшом примере.

Задача:

> После оформления заказа нужно изменить состояние заказа и отправить пользователю уведомление.

У нас есть несколько ответственностей:

```text
Order
→ состояние заказа

OrderService
→ сценарий оформления

MessageSender
→ контракт отправки сообщения

EmailSender
→ конкретный способ отправки
```

## `Order` отвечает за своё состояние

```java
class Order {
    private boolean completed;

    public void complete() {
        completed = true;
    }

    public boolean isCompleted() {
        return completed;
    }
}
```

Здесь работает инкапсуляция:

```text
private boolean completed
↓
снаружи нельзя изменить напрямую
```

Внешний код использует осмысленную операцию:

```java
order.complete();
```

а не прямую запись поля.

## `MessageSender` задаёт контракт

```java
interface MessageSender {
    void send(String message);
}
```

Контракт минимальный:

```text
объект умеет отправить строку
```

Конкретная реализация:

```java
class EmailSender implements MessageSender {

    public void send(String message) {
        System.out.println("Email: " + message);
    }
}
```

## `OrderService` координирует сценарий

```java
class OrderService {
    private MessageSender sender;

    public OrderService(MessageSender sender) {
        this.sender = sender;
    }

    public void complete(Order order) {
        order.complete();
        sender.send("Order completed");
    }
}
```

Разберём метод:

```java
public void complete(Order order) {
    order.complete();
    sender.send("Order completed");
}
```

Шаг 1:

```text
OrderService
↓
просит Order
изменить своё состояние
```

Шаг 2:

```text
OrderService
↓
просит MessageSender
отправить уведомление
```

`OrderService` не меняет поле `completed` напрямую. Он вызывает:

```java
order.complete();
```

То есть состояние остаётся ответственностью `Order`.

И `OrderService` не реализует отправку email внутри себя. Он вызывает:

```java
sender.send(...);
```

То есть отправка делегируется другому объекту.

## Что здесь использовано

### Инкапсуляция

```java
private boolean completed;
```

Состояние скрыто.

### Публичный контракт класса

```java
order.complete();
order.isCompleted();
```

Внешнему коду доступны понятные операции.

### Ответственность

```text
Order
→ состояние заказа

OrderService
→ сценарий

MessageSender
→ отправка сообщения
```

### Композиция / связь объектов

```java
private MessageSender sender;
```

`OrderService` хранит ссылку на другой объект.

### Делегирование

```java
sender.send("Order completed");
```

Работа передаётся отправителю.

### Интерфейс

```java
interface MessageSender
```

описывает требуемое поведение.

# 17. Меняем реализацию без изменения сервиса

Добавим другую реализацию:

```java
class ConsoleSender implements MessageSender {

    public void send(String message) {
        System.out.println(message);
    }
}
```

Теперь можно создать сервис так:

```java
MessageSender sender = new ConsoleSender();
OrderService service = new OrderService(sender);
```

Сам класс `OrderService` не изменился.

```text
OrderService
→ знает, когда нужно отправить сообщение

ConsoleSender
→ знает, как именно его отправить
```

Каждый объект отвечает за свою часть задачи.

# 18. Типичные ошибки

## Ошибка 1. Публичные поля

Плохой вариант:

```java
class BankAccount {
    public int balance;
}
```

Теперь любой код может сделать:

```java
account.balance = -5000;
```

Проблема:

```text
внешний код
↓
обходит правила объекта
↓
класс не может гарантировать корректное состояние
```

Лучше:

```java
class BankAccount {
    private int balance;

    public void deposit(int amount) {
        if (amount > 0) {
            balance += amount;
        }
    }
}
```

---

## Ошибка 2. Setter для каждого поля

Плохая автоматическая привычка:

```java
private int balance;

public void setBalance(int balance) {
    this.balance = balance;
}
```

Такой метод снова разрешает произвольное изменение.

Лучше задавать операции предметной области:

```java
deposit(...)
withdraw(...)
```

Главный вопрос:

> Какие действия действительно имеет смысл разрешить объекту?

---

## Ошибка 3. Один класс делает всё

Представим:

```text
Order
├── хранит состояние
├── считает стоимость
├── сохраняет файл
├── печатает документ
├── отправляет email
└── управляет пользователями
```

Проблема не в количестве строк само по себе.

Проблема в смешивании несвязанных обязанностей.

Полезно попробовать разделить:

```text
Order
→ заказ

MessageSender
→ уведомления

ReceiptPrinter
→ печать
```

На этой неделе не нужно строить сложную архитектуру.

Достаточно научиться замечать, когда класс перестаёт иметь одну понятную зону ответственности.

---

## Ошибка 4. Интерфейс ради интерфейса

Сам по себе `interface` не делает дизайн хорошим.

Не нужно рассуждать так:

```text
«У нас ООП»
↓
«значит для каждого класса нужен interface»
```

Полезный вопрос:

> Какую роль или заменяемое поведение этот интерфейс выражает?

Для `MessageSender` ответ понятен:

```text
нужно уметь отправить сообщение
↓
способ отправки может различаться
```

Поэтому контракт естественен.

---

## Ошибка 5. Отношение «содержит» пытаются выразить как «является»

Представим связь:

```text
Car имеет Engine
```

Рабочая модель:

```java
class Car {
    private Engine engine;
}
```

Здесь автомобиль использует двигатель как часть своей структуры.

Это отношение:

```text
содержит
```

Подробное сравнение композиции и наследования будет на следующей неделе.

# 19. Как проектировать маленькую объектную модель

Попробуем сформулировать простой порядок действий.

Допустим, дана предметная задача.

## Шаг 1. Найти состояние

Какие данные нужно хранить?

Например:

```text
Order
→ completed
```

## Шаг 2. Найти правила

Какие состояния допустимы?

Какие операции должны контролировать изменения?

```text
Order
↓
complete()
```

## Шаг 3. Найти ответственности

Кто отвечает за каждую часть сценария?

```text
Order
→ состояние заказа

OrderService
→ оформление

MessageSender
→ уведомление
```

## Шаг 4. Найти связи

Кому нужен другой объект?

```text
OrderService
↓
MessageSender
```

## Шаг 5. Решить, нужен ли контракт

Если конкретная реализация может меняться, полезно выразить требуемое поведение интерфейсом:

```java
interface MessageSender {
    void send(String message);
}
```

Получается модель:

```text
задача
↓
состояния и правила
↓
ответственности
↓
классы
↓
связи
↓
контракты
```

# 20. Итоговая модель недели

Начинали мы с отдельного объекта:

```text
объект
=
состояние + поведение
```

Но этого недостаточно для небольшой системы.

Добавляем инкапсуляцию:

```text
объект
↓
контролирует своё состояние
```

Добавляем инварианты:

```text
публичные операции
↓
сохраняют правила корректности
```

Отделяем внешний контракт:

```text
публичные методы
↓
что объект позволяет делать
```

Определяем ответственность:

```text
класс
↓
понятная часть задачи
```

Связываем объекты:

```text
объект
↓
содержит / использует
другой объект
```

Это композиция.

Передаём работу:

```text
объект A
↓
вызывает объект B
↓
объект B выполняет свою часть
```

Это делегирование.

Если конкретный класс не важен, а важно поведение:

```text
нужна роль
↓
interface
↓
несколько возможных реализаций
```

Итог:

```text
объект
=
состояние + поведение

↓

инкапсуляция
=
контроль состояния

↓

инвариант
=
правила объекта

↓

публичный контракт
=
доступные операции

↓

ответственность
=
часть задачи

↓

композиция
=
связь объектов

↓

делегирование
=
передача работы

↓

interface
=
контракт поведения
```

# 21. Что нужно уметь после этой темы

После недели 4 важно уметь смотреть на небольшую задачу не только как на последовательность команд.

Нужно уметь задавать вопросы:

- Какие объекты есть в задаче?
- Какое состояние принадлежит каждому объекту?
- Какие правила должен защищать сам объект?
- Что должно быть `private`?
- Какие операции должны быть доступны снаружи?
- За что отвечает каждый класс?
- Не делает ли один класс слишком много?
- Какие объекты должны содержать или использовать другие объекты?
- Где работу можно делегировать?
- Нужен ли конкретный класс или достаточно контракта поведения?

Это переход:

```text
«я умею написать класс»
↓
«я умею разделить задачу
между несколькими объектами»
```

# 22. Небольшая задача перед семинаром

Нужно спроектировать простую систему оплаты заказа.

Есть объект:

```text
Order
```

После успешной оплаты его состояние должно измениться.

Оплата может выполняться разными способами, например:

```text
CardPaymentProcessor

3. Какие публичные операции нужны `Order`?

операции, доступные внешнему коду
```

## Ответственность класса

```text
одна понятная часть задачи
```

## Композиция

```text
объект содержит / использует другой объект
```

## Делегирование

```text
объект передаёт работу другому объекту
```

## `interface`

```text
контракт требуемого поведения
```

## `implements`

```text
класс предоставляет реализацию контракта
```

## Главная идея недели

> Объектно-ориентированная программа — это не просто набор классов. Это система объектов с понятными ответственностями, защищённым состоянием и небольшими контрактами взаимодействия.
