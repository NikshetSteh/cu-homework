# 1. Консольный ввод, пути и окружение

## Задача 1. Почему приложение читает не тот конфиг

**Обязательная**

**Ориентировочное время:** 15 минут

Есть структура проекта:

```text
deploy-tool/
├── configs/
│   ├── local/
│   │   └── app.conf
│   └── demo/
│       └── app.conf
├── sandbox/
│   └── configs/
│       └── local/
│           └── app.conf
└── src/
    └── Main.java

```

Содержимое файлов:

`configs/local/app.conf`

```text
endpoint=http://localhost:8080

```

`sandbox/configs/local/app.conf`

```text
endpoint=http://sandbox:8080

```

Программа:

```java
Path config =
        Path.of(
                "configs",
                "local",
                "app.conf"
        );

System.out.println(
        Files.readString(config)
);

```

Один разработчик запускает программу с working directory:

```text
deploy-tool/

```

Другой:

```text
deploy-tool/sandbox/

```

### Часть 1. Анализ без запуска

Ответь:

1. Какой файл прочитает первый запуск?
2. Какой файл прочитает второй запуск?
3. Почему Java-код при этом полностью одинаковый?
4. Что изменится в результате `config.toAbsolutePath()`?
5. Почему путь не считается относительно `Main.java`?

### Часть 2. Диагностика

Добавь в программу вывод:

```text
working directory
relative path
absolute path
exists
isRegularFile

```

### Часть 3. Рефакторинг

Теперь пользователь при запуске вводит профиль:

```text
local
или
demo

```

Нужно построить путь:

```text
configs/<profile>/app.conf

```

через `Path`, без ручной конкатенации `/` и `\`.

Если профиль неизвестен, программу не нужно пытаться запускать с произвольным путём.

### Пример 1

```text
Ввод:
local

Working directory:
.../deploy-tool

Результат:
endpoint=http://localhost:8080

```

### Пример 2

```text
Ввод:
unknown

Результат:
Unknown profile

```

# 2. Потоковая обработка данных

## Задача 2. Аудит шлюза платежей

**Обязательная**

**Ориентировочное время:** 25 минут

Есть файл:

```text
gateway.log

```

Каждая корректная строка имеет формат:

```text
requestId|status|latencyMs|amount

```

Где:

```text
requestId
→ непустая строка

status
→ OK или REJECTED

latencyMs
→ целое число >= 0

amount
→ целое число > 0

```

Пример файла:

```text
r-1001|OK|120|500
r-1002|REJECTED|87|900
r-1003|OK|340|1500
broken-line
r-1004|OK|oops|700
r-1005|REJECTED|410|1200
r-1006|REJECTED|390|300
r-1007|OK|65|800

```

Создай класс:

```text
GatewayRecord

```

с данными одной корректной записи.

Программа должна читать файл **построчно** и не хранить все записи в памяти.

Для корректных записей нужно вычислить:

```text
общее количество корректных записей
количество OK
количество REJECTED
суммарную amount только для OK
максимальную latencyMs
самую длинную последовательность подряд идущих REJECTED

```

Некорректную строку нужно:

```text
не включать в статистику
+
увеличить счётчик malformed

```

После обработки создай файл:

```text
gateway-report.txt

```

с форматом:

```text
Valid: <число>
Malformed: <число>
OK: <число>
Rejected: <число>
Successful amount: <число>
Max latency: <число>
Longest rejected streak: <число>

```

### Пример

Для файла выше отчёт должен содержать:

```text
Valid: 6
Malformed: 2
OK: 3
Rejected: 3
Successful amount: 2800
Max latency: 410
Longest rejected streak: 2

```

### Требования

Используй:

```text
BufferedReader
BufferedWriter
UTF-8
try-with-resources

```

Раздели хотя бы две ответственности:

```text
разбор одной строки
обработка уже разобранной записи

```

Не помещай всё в один огромный `main`.

### Ограничения

Не используй:

- коллекции;
- Stream API;
- `Files.readAllLines(...)`;
- `Files.lines(...)`.

### После решения

Ответь:

1. Какое состояние нужно хранить между итерациями для серии `REJECTED`?
2. Почему весь файл не нужно загружать в память?
3. Какие ошибки здесь относятся к содержимому строки, а какие — к I/O?

# 3. Рефакторинг кода с ресурсами

## Задача 3. Метод работает, пока не сработал `return`

**Обязательная**

**Ориентировочное время:** 15 минут

В проекте есть метод поиска первой строки с критической записью:

```java
static String findCritical(Path path) {
    try {
        BufferedReader reader =
                Files.newBufferedReader(path);

        String line;

        while ((line = reader.readLine()) != null) {
            if (line.startsWith("CRITICAL|")) {
                return line;
            }
        }

        reader.close();

        return null;

    } catch (Exception e) {
        System.out.println("Something went wrong");
        return null;
    }
}

```

Код проходит обычные ручные проверки, но ревьюер просит его переработать.

### Часть 1. Code review

Найди минимум **четыре проблемы**.

Среди них должны быть проблемы разных типов:

```text
жизненный цикл ресурса
обработка исключений
контракт возвращаемого значения
ответственность метода

```

Не ограничивайся стилем форматирования.

### Часть 2. Рефакторинг

Переработай метод так, чтобы:

- ресурс гарантированно закрывался;
- `catch (Exception e)` исчез;
- ошибка чтения не смешивалась с результатом «строка не найдена»;
- вызывающий код мог самостоятельно решить, что делать при I/O-ошибке.

### Пример 1

Файл:

```text
INFO|boot
WARN|cache
CRITICAL|database
INFO|retry

```

Результат поиска:

```text
CRITICAL|database

```

### Пример 2

Файл:

```text
INFO|boot
WARN|cache
INFO|finish

```

Результат поиска:

```text
null

```

### Дополнительный вопрос

Почему:

```text
файл не удалось прочитать

```

и:

```text
в файле нет CRITICAL

```

не должны выглядеть для вызывающего кода одинаково?

# 4. Кодировка как контракт между двумя программами

## Задача 4. Экспортёр и импортёр не договорились

**Обязательная**

**Ориентировочное время:** 10 минут

Две программы принадлежат разным командам.

Экспортёр пишет файл:

```java
Files.writeString(
        path,
        "Москва|Склад-7|готово",
        Charset.forName("windows-1251")
);

```

Импортёр читает его:

```java
String line =
        Files.readString(
                path,
                StandardCharsets.UTF_8
        );

```

После интеграции импортёр получает искажённый текст.

### Часть 1. Эксперимент

1. Воспроизведи ситуацию.
2. Прочитай файл обеими кодировками.
3. Получи `byte[]` через `Files.readAllBytes(...)`.
4. Убедись, что чтение разными кодировками не переписывает файл.

### Часть 2. Контракт

Представь, что код экспортёра менять нельзя.

Исправь импортёр.

После этого коротко опиши контракт обмена файлом:

```text
разделитель
порядок полей
кодировка

```

### Пример 1

```text
Правильное чтение:
Москва|Склад-7|готово

```

### Пример 2

```text
Неправильная кодировка:
<искажённый текст>

```

Точный вид искажённой строки зависит от используемых символов и среды.

### После решения

Ответь:

> Почему нельзя сказать, что «файл хранится в неправильной строке», если сами байты были записаны корректно?

# 5. Одновременная работа с несколькими файлами

## Задача 5. Слияние журналов

**Обязательная**

**Ориентировочное время:** 20 минут

Есть два текстовых файла с событиями двух серверов.

Каждый файл уже отсортирован по времени.

`server-a.log`:

```text
09:01|A|started
09:05|A|request accepted
09:11|A|cache cleared
09:20|A|stopped
```

`server-b.log`:

```text
09:02|B|started
09:07|B|connection opened
09:15|B|request rejected
09:18|B|connection closed
```

Нужно создать общий файл:

```text
merged.log
```

в котором события из двух файлов идут в хронологическом порядке:

```text
09:01|A|started
09:02|B|started
09:05|A|request accepted
09:07|B|connection opened
09:11|A|cache cleared
09:15|B|request rejected
09:18|B|connection closed
09:20|A|stopped
```

### Важно

Файлы могут быть большими.

Нельзя:

```text
прочитать оба файла целиком
↓
сохранить все строки в памяти
↓
объединить
↓
отсортировать
```

Нужно читать оба файла **постепенно**.

В каждый момент достаточно помнить:

```text
текущую строку server-a.log
+
текущую строку server-b.log
```

Сравнивай время текущих событий и записывай в `merged.log` то событие, которое должно идти раньше.

После записи получай следующую строку только из соответствующего файла.

---

### Формат времени

Для этой задачи время всегда имеет формат:

```text
HH:mm
```

и содержит ведущий ноль:

```text
09:05
14:30
```

Поэтому для определения порядка можно использовать первые пять символов строки.

Не нужно использовать API для работы с датами и временем.

---

### Пример 1

`server-a.log`:

```text
08:10|A|started
08:30|A|finished
```

`server-b.log`:

```text
08:20|B|started
08:25|B|finished
```

`merged.log`:

```text
08:10|A|started
08:20|B|started
08:25|B|finished
08:30|A|finished
```

---

### Пример 2

`server-a.log`:

```text
10:00|A|started
10:05|A|working
10:10|A|finished
```

`server-b.log`:

```text
10:03|B|started
```

`merged.log`:

```text
10:00|A|started
10:03|B|started
10:05|A|working
10:10|A|finished
```

Обрати внимание: один файл может закончиться раньше другого.

---

### Требования

Используй:

```text
два BufferedReader
+
один BufferedWriter
+
try-with-resources
+
UTF-8
```

Все три ресурса должны корректно закрываться.

### Ограничения

Не используй:

- коллекции;
- Stream API;
- `Files.readAllLines(...)`;
- `Files.lines(...)`;
- сортировку готового набора строк.

---

### После решения

Ответь:

1. Какое минимальное состояние нужно хранить между итерациями?
2. Почему после записи строки нужно читать следующую строку только из одного файла?
3. Что должно произойти, когда один из файлов закончился раньше другого?
4. Почему объём памяти этого решения почти не зависит от размера исходных файлов?
5. Что произойдёт при `IOException` во время чтения одного из файлов и кто должен принять решение о реакции?

**Обязательная**

**Ориентировочное время:** 15 минут

Есть журнал команд:

```text
BEGIN
STEP|compile
STEP|test
END

```

Допустимый блок должен:

```text
начинаться с BEGIN
заканчиваться END
между ними содержать STEP

```

Файл читается построчно.

Нужно определить:

```text
количество полностью завершённых блоков
количество незавершённых блоков
количество STEP вне блока

```

### Пример

```text
BEGIN

END
STEP|outside
BEGIN
STEP|deploy

```

Результат:

```text
Completed: 1
Unfinished: 1
Steps outside block: 1

```

### Ограничение

Не храни все строки файла.

Path exportRoot =

### Пример

```text
Результат:

```

### Ограничение

Не конкатенируй путь строками.
