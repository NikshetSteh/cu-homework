# Java 1. Неделя 2 — Git через IntelliJ IDEA

## Лонгрид для самостоятельного изучения

На этой неделе мы знакомимся с Git не как с набором команд терминала, а как с **моделью работы с историей проекта**.

Основной рабочий инструмент курса — **IntelliJ IDEA**. Большинство действий мы будем выполнять через интерфейс IDE, но для каждого действия будем понимать:

```text
что это означает в Git
↓
где это находится в IntelliJ IDEA
↓
какой Git-команде это соответствует
```

Главная цель — не выучить десятки команд наизусть.

Нужно научиться понимать, **что происходит с проектом**, когда вы нажимаете `Commit`, `Push`, `Fetch`, переключаете ветку или разрешаете конфликт.

> IntelliJ IDEA не заменяет Git. Она даёт удобный интерфейс для работы с Git.

---

# 1. Зачем вообще нужен Git

Представим обычный учебный проект:

```text
java-course/
├── src/
│   ├── Main.java
│   └── Calculator.java
└── README.md
```

Утром программа работает.

Потом вы:

```text
изменили Calculator.java
↓
добавили новый метод
↓
переписали Main.java
↓
удалили старый код
↓
вечером программа перестала работать
```

Возникают вопросы:

- что именно я поменял;
- какой код был до изменений;
- когда появилась ошибка;
- как сохранить рабочую версию;
- как показать преподавателю своё решение;
- как получить новые материалы курса;
- как двум людям работать с одним проектом.

Если просто делать копии папок:

```text
project-final/
project-final2/
project-final-real/
project-final-real-last/
```

очень быстро становится непонятно, где какая версия.

Git решает эту проблему системно.

## Основная идея Git

Git хранит **историю состояний проекта**.

Упрощённо:

```text
рабочая версия
↓
изменения
↓
commit
↓
новая точка истории
```

Например:

```text
A --- B --- C
```

Где:

```text
A
→ начальная версия

B
→ добавили решение задачи

C
→ исправили ошибку
```

Теперь можно понять, как проект менялся со временем.

### Главное

```text
Git
→ история изменений проекта
```

---

# 2. Git и GitLab — не одно и то же

Это одна из первых вещей, которые легко перепутать.

## Git

Git — программа и система контроля версий.

Она может работать полностью локально:

```text
ваш компьютер
↓
Git
↓
история commits
```

Интернет для этого не нужен.

Можно:

- создать repository;
- изменить файлы;
- делать commits;
- создавать ветки;
- смотреть историю.

## GitLab

GitLab — серверная платформа, на которой можно хранить Git-репозитории.

Упрощённо:

```text
Git
→ управляет версиями

GitLab
→ хранит удалённую копию repository
→ показывает Merge Requests
→ позволяет делать review
→ запускает CI, если он настроен
```

На курсе GitLab нужен, чтобы:

- получать задания;
- отправлять решения;
- хранить ветки домашних работ;
- создавать Merge Request;
- проверять работу преподавателем.

### Главное

```text
Git
≠
GitLab

Git
→ механизм

GitLab
→ сервер и интерфейс вокруг Git
```

---

# 3. Repository

## Проблема

Git должен понимать:

> Какие файлы относятся к одному проекту и какую историю нужно хранить?

Для этого существует **repository**, или репозиторий.

## Основная идея

Repository — это проект, за историей которого следит Git.

Например:

```text
java-course/
├── src/
│   ├── Main.java
│   └── Calculator.java
├── README.md
└── .git/
```

Каталог:

```text
.git/
```

хранит служебную информацию Git.

Обычно вручную внутрь `.git` заходить не нужно.

Удаление `.git` фактически превращает папку в обычную папку без Git-истории.

---

## Local repository

Это репозиторий на вашем компьютере.

Именно с ним вы работаете в IntelliJ IDEA:

```text
открыли проект
↓
изменили Main.java
↓
запустили программу
↓
посмотрели diff
↓
сделали commit
```

---

## Remote repository

Это репозиторий на другом компьютере, обычно на сервере.

На курсе:

```text
GitLab
→ remote repository
```

Важно понимать:

```text
local repository
и
remote repository

могут находиться
в разных состояниях
```

Например:

```text
локально:
A --- B --- C

GitLab:
A --- B
```

Commit `C` уже существует на вашем компьютере, но ещё не отправлен на сервер.

### В IntelliJ IDEA

IDEA автоматически понимает, что открытая папка является Git-репозиторием.

Появляются:

- Git tool window;
- Commit tool window;
- виджет текущей ветки;
- Push / Pull / Fetch;
- Git Log.

### CLI-эквивалент

Чтобы посмотреть состояние repository:

```bash
git status
```

### Главное

```text
repository
→ проект + его Git-история
```

---

# 4. Git в IntelliJ IDEA

IntelliJ IDEA не реализует отдельную систему контроля версий вместо Git.

IDE использует установленный Git.

Проверить это можно:

```text
Settings
→ Version Control
→ Git
```

Там находится:

```text
Path to Git executable
```

Например:

```text
/usr/bin/git
```

или на Windows:

```text
C:\Program Files\Git\bin\git.exe
```

Кнопка:

```text
Test
```

проверяет, что IDEA может запустить Git.

По смыслу это соответствует проверке:

```bash
git --version
```

## Почему это важно

Когда вы нажимаете:

```text
Commit
Push
Fetch
Merge
Rebase
```

это не «операции IntelliJ IDEA».

Это **Git-операции**, для которых IDEA предоставляет графический интерфейс.

В дальнейшем удобно мыслить так:

```text
IDEA
→ интерфейс

Git
→ механизм
```

# 5. Clone — получить проект с GitLab

## Проблема

Репозиторий уже существует в GitLab.

Нам нужна его локальная копия.

Можно было бы вручную скачать файлы, но тогда мы не получили бы Git-историю и связь с сервером.

Для этого существует `clone`.

## Основная идея

```text
remote repository
↓
clone
↓
local repository
```

После clone получаем:

- файлы проекта;
- историю commits;
- сведения о ветках;
- связь с удалённым репозиторием.

---

## Через IntelliJ IDEA

На Welcome Screen:

```text
Get from VCS
```

или:

```text
File
→ New
→ Project from Version Control
```

Дальше:

```text
URL репозитория
↓
локальная папка
↓
Clone
```

После этого IDEA открывает уже готовый локальный Git-репозиторий.

---

## Что происходит под капотом

CLI-эквивалент:

```bash
git clone <url>
```

Например:

```bash
git clone git@git.culab.ru:student/java-course.git
```

Git:

```text
создаёт папку
↓
скачивает repository
↓
создаёт .git
↓
запоминает адрес сервера
```

После обычного clone сервер автоматически получает имя:

```text
origin
```

### Главное

```text
Clone
→ не просто скачать файлы
→ создать полноценную локальную копию Git repository
```

---

# 6. Remote

## Зачем нужен remote

У локального Git должны быть сохранены адреса репозиториев, с которыми он взаимодействует.

Такая сохранённая ссылка называется **remote**.

На курсе будут особенно важны два:

```text
origin
upstream
```

---

## `origin`

После clone Git обычно автоматически создаёт:

```text
origin
```

Для курса:

```text
origin
→ ваш личный GitLab-репозиторий 
```

Именно туда вы будете отправлять решение.

---

## `upstream`

Дополнительно подключаем шаблон курса:

```text
upstream
→ репозиторий преподавателя
→ оттуда появляются новые ДЗ
```

Получается:

```text
Шаблон курса
    upstream
       ↓
локальный repository
       ↓
     origin
       ↓
Ваш личный GitLab 
```

---

## В IntelliJ IDEA

Remote можно посмотреть через Git-инструменты IDEA, например:

```text
Git
→ Manage Remotes
```

Название пункта может немного отличаться между версиями IDE.

---

## Под капотом

Посмотреть remotes:

```bash
git remote -v
```

Например:

```text
origin    git@git.culab.ru:students/ivan.git
upstream  git@git.culab.ru:courses/java-template.git
```

Добавить `upstream`:

```bash
git remote add upstream <url>
```

### Важное различие

```text
origin
→ куда отправляем свою работу

upstream
→ откуда получаем задания
```

---

# 7. Что происходит после изменения файла

Есть commit:

```text
A
```

Он содержит состояние проекта.

Теперь изменим:

```java
System.out.println("Hello");
```

на:

```java
System.out.println("Hello, Git");
```

Файл на диске уже отличается от версии, сохранённой в последнем commit.

Git видит:

```text
последний commit
≠
рабочая версия файла
```

Это называется **изменение рабочего дерева**.

Не обязательно сейчас запоминать термин `working tree`, но полезно понимать модель:

```text
последняя сохранённая версия Git
↓
ваши текущие файлы
↓
между ними есть разница
```

# 8. Status — что сейчас происходит

Когда в Git что-то непонятно, первый полезный вопрос:

> В каком состоянии мой repository?

Для этого существует `status`.

## Что он показывает

Например:

- в какой ветке мы находимся;
- какие файлы изменены;
- какие файлы новые;
- какие изменения подготовлены к commit;
- идёт ли merge;
- идёт ли rebase.

---

## В IntelliJ IDEA

Состояние файлов видно сразу в нескольких местах:

```text
Project
Commit tool window
Git tool window
```

IDEA визуально отмечает изменённые файлы.

---

## Под капотом

```bash
git status
```

Например:

```text
On branch hw-03

Changes not staged for commit:
    modified: src/Main.java
```

### Практическое правило

```text
не понимаю, что происходит
↓
git status
```

Даже если вы в основном используете IDEA, эта команда очень полезна для диагностики.

# 9. Diff — что именно изменилось

Знать, что файл изменён, недостаточно.

Нужно ответить:

> Что именно поменялось?

Для этого используется **diff**.

Было:

```java
System.out.println("Hello");
```

Стало:

```java
System.out.println("Hello, Git");
```

Diff показывает идею:

```diff
- System.out.println("Hello");
+ System.out.println("Hello, Git");
```

Условно:

```text
-
→ было

+
→ стало
```

---

## Diff в IntelliJ IDEA

Самый удобный вариант:

```text
Commit tool window
↓
выбрать файл
↓
IDEA показывает diff
```

Также diff доступен:

- из Git Log;
- через контекстное меню файла;
- через цветовые маркеры в editor.

---

## Под капотом

CLI:

```bash
git diff
```

---

## Почему diff нужно смотреть до commit

Представим, программа работает, но в коде осталось:

```java
System.out.println("DEBUG");
```

Или вы случайно изменили `README.md`.

Или в commit собирается попасть временный файл.

Diff позволяет увидеть это до сохранения истории.

### Хорошая привычка

```text
изменили код
↓
посмотрели diff
↓
только потом commit
```

> Commit начинается не с кнопки Commit. Он начинается с проверки изменений.

---

# 10. Commit

## Проблема

Мы изменили код и хотим зафиксировать это состояние в истории.

Для этого создаётся **commit**.

## Основная идея

Было:

```text
A --- B
```

После commit:

```text
A --- B --- C
```

`C` — новая точка истории.

---

## Что хранит commit

Упрощённо commit содержит:

- состояние изменений проекта;
- автора;
- email автора;
- время;
- commit message;
- ссылку на родительский commit.

Важно:

> Commit создаётся локально.

GitLab пока может ничего не знать про него.

---

## Commit в IntelliJ IDEA

Открываем:

```text
Commit tool window
```

Рабочий процесс:

```text
посмотреть изменённые файлы
↓
выбрать нужные
↓
посмотреть diff
↓
написать message
↓
Commit
```

---

## Что происходит под капотом

CLI-модель обычно выглядит так:

```bash
git add .
git commit -m "Complete hw-03"
```

Здесь появляется ещё одна сущность — подготовленные изменения.

Для первого знакомства достаточно понимать:

```text
git add
→ выбрать изменения для следующего commit

git commit
→ создать commit
```

Глубоко разбирать staging area пока не требуется.

IDEA умеет скрыть часть этой механики и дать выбрать нужные изменения прямо в Commit window.

---

# 11. Commit message

У каждого commit есть сообщение.

Оно должно отвечать примерно на вопрос:

> Что изменилось?

Плохо:

```text
aaa
123
fix
test
```

Лучше:

```text
Complete hw-03
Add validation for age
Fix maximum calculation
```

Через неделю история:

```text
fix
fix
123
aaa
```

почти бесполезна.

А:

```text
Add file import
Fix invalid score handling
Complete report generation
```

уже помогает понять развитие проекта.

### В IntelliJ IDEA

Commit message вводится прямо в Commit tool window.

### Под капотом

```bash
git commit -m "Complete hw-03"
```

---

# 12. Commit не равен Push

Это одна из самых важных моделей семинара.

После commit:

```text
локально:
A --- B --- C

GitLab:
A --- B
```

Commit `C` существует.

Но только на вашем компьютере.

Чтобы он появился в GitLab, нужен `Push`.

```text
Commit
→ локальная история

Push
→ отправить локальную историю на сервер
```

Типичная ситуация:

> «Я сделал commit, но преподаватель не видит решение».

Очень часто причина:

```text
commit сделали
↓
push забыли
```

---

# 13. Push

## Основная идея

Push передаёт локальные commits в remote repository.

До:

```text
local:
A --- B --- C

origin:
A --- B
```

После:

```text
local:
A --- B --- C

origin:
A --- B --- C
```

---

## В IntelliJ IDEA

```text
Git
→ Push
```

Перед отправкой IDEA показывает:

- текущую ветку;
- destination;
- commits, которые будут отправлены.

Нужно посмотреть, что отправляется именно нужная ветка.

---

## Под капотом

Обычный push:

```bash
git push
```

Для новой ветки первый раз:

```bash
git push -u origin hw-03
```

`-u` связывает:

```text
local hw-03
↕
origin/hw-03
```

После этого в дальнейшем достаточно:

```bash
git push
```

---

# 14. Fetch

Представим:

```text
local main:
A --- B

remote main:
A --- B --- C
```

На сервере уже существует новый commit `C`, но локальный Git пока про него может не знать.

Нужно получить информацию с сервера.

Для этого есть `fetch`.

## Главное свойство Fetch

Fetch **не изменяет текущую локальную ветку**.

После:

```bash
git fetch origin
```

получаем примерно:

```text
main
A --- B

origin/main
A --- B --- C
```

То есть Git уже знает про `C`, но локальный `main` всё ещё находится на `B`.

---

## В IntelliJ IDEA

```text
Git
→ Fetch
```

---

## Для курса

Новое ДЗ появляется в `upstream`.

Поэтому:

```bash
git fetch upstream
```

означает:

```text
сходить в шаблон курса
↓
получить новые commits и branches
↓
не менять текущую рабочую ветку
```

### Главное

```text
Fetch
→ узнать, что нового на remote
→ не менять текущую branch
```

---

# 15. Pull

Иногда мы хотим не только узнать про изменения, но и сразу обновить текущую ветку.

Для этого есть `pull`.

Упрощённо:

```text
Pull
=
Fetch
+
интеграция
```

То есть:

```text
remote
↓
скачать изменения
↓
встроить их в current branch
```

---

## В IntelliJ IDEA

```text
Git
→ Pull
```

или через действие обновления проекта.

---

## Под капотом

```bash
git pull
```

Концептуально:

```text
git pull
≈
git fetch
+
merge или rebase
```

Как именно интегрируются изменения, зависит от настроек Git.

---

# 16. Fetch vs Pull

Эти две операции важно не путать.

| | Fetch | Pull |
|---|---|---|
| Скачать новые commits | да | да |
| Обновить remote branches | да | да |
| Изменить текущую local branch | нет | да |
| Автоматически интегрировать изменения | нет | да |

Упрощённая модель:

```text
Fetch
→ «покажи, что нового»

Pull
→ «получи и обнови мою текущую ветку»
```

Для получения новых домашних заданий нам нужен:

```bash
git fetch upstream
```

Потому что задача:

```text
получить новую ветку hw-03
```

а не:

```text
влить hw-03
в текущую рабочую ветку
```

---

# 17. Branch

## Зачем нужны ветки

Представим, есть стабильная история:

```text
A --- B --- C   main
```

Мы хотим начать новое ДЗ, не меняя `main`.

Создаём:

```text
hw-03
```

Получается:

```text
A --- B --- C   main
             \
              D --- E   hw-03
```

Теперь commits `D` и `E` относятся к работе над `hw-03`.

---

## Что такое branch на самом деле

Упрощённо удобно говорить:

```text
branch
→ отдельная линия работы
```

Но технически branch — это **указатель на commit**.

Например:

```text
main
↓
C
```

и:

```text
hw-03
↓
E
```

Когда в `hw-03` создаётся новый commit:

```text
E --- F
```

указатель автоматически передвигается:

```text
hw-03
↓
F
```

---

## В IntelliJ IDEA

Текущая ветка отображается в Git / VCS widget.

По клику открывается список branches.

---

## Под капотом

Посмотреть ветки:

```bash
git branch
```

Переключиться:

```bash
git switch hw-03
```

### Важная привычка

Перед началом работы:

```text
посмотреть текущую ветку
↓
только потом менять код
```

# 18. Remote branch и local branch

После `fetch upstream` мы можем увидеть:

Это не наша локальная рабочая ветка.

Это локальное представление состояния ветки на remote.

Чтобы работать, создаём:

```text

```

на её основе.

```text
upstream/hw-03
→ состояние задания

→ наша локальная рабочая ветка

origin/hw-03
→ наша опубликованная ветка в GitLab
```

Это три разные сущности.

Схема:

```text
upstream/hw-03
      ↓
    hw-03
      ↓
origin/hw-03
```

# 20. Switch и Checkout

В старых инструкциях часто встречается:

```bash
git checkout main
```

Современный вариант:

```bash
git switch main
```

Почему появились две команды?

Потому что `checkout` исторически умеет слишком много:

```text
checkout
├── переключать ветки
├── переходить на commit
└── восстанавливать файлы
```

Позже Git разделил эти задачи:

```text
switch
→ работа с branches

restore
→ восстановление файлов
```

На курсе для CLI лучше использовать:

```bash
git switch
```

Но в интерфейсе IDEA слово:

```text
Checkout
```

может всё ещё встречаться.

Это нормально.

# 21. История Git — это не обязательно линия

Пока мы видели:

```text
A --- B --- C
```

Но Git-история может ветвиться.

Например:

```text
A --- B --- C   main
       \
        D --- E   feature
```

На самом деле история Git — граф.

Обычный commit обычно имеет одного родителя:

```text
C
↓ parent
B
```

Первый commit не имеет родителя.

Merge commit может иметь двух родителей.

Именно поэтому Git умеет хранить разошедшиеся и позже объединённые линии работы.

---

# 22. Merge

## Проблема

Есть две линии истории:

```text
A --- B --- C   main
       \
        D --- E   feature
```

Нужно их объединить.

Один способ — `merge`.

## Основная идея

Находясь в `feature`:

```bash
git merge main
```

Git объединяет изменения.

Может появиться:

```text
A --- B --- C
       \     \
        D --- E --- M   feature
```

`M` — **merge commit**.

---

## Почему у M два родителя

```text
M
├── parent → E
└── parent → C
```

Git фиксирует факт:

> Эти две истории были объединены здесь.

Сам commit `C` не копируется внутрь `M`.

`M` хранит итоговое состояние объединённого проекта и ссылки на обоих родителей.

---

## В IntelliJ IDEA

Обычно:

```text
Branches
↓
выбрать другую branch
↓
Merge into Current
```

Очень важно смотреть:

```text
Current branch
```

потому что merge выполняется **в текущую ветку**.

Если current:

```text
feature
```

и выбираем:

```text
main → Merge into Current
```

получаем:

```text
main
→ вливается в feature
```

а не наоборот.

---

## Под капотом

```bash
git merge main
```

### Главное

```text
Merge
→ объединяет истории
→ существующие commits не переписывает
```

---

# 23. Fast-forward: простой случай merge

Иногда ветки фактически не разошлись.

Было:

```text
A --- B --- C   main
             \
              D --- E   feature
```

`main` не менялся после создания feature.

Тогда для объединения не всегда нужен отдельный merge commit.

Git может просто передвинуть:

```text
main
```

на:

```text
E
```

Получится:

```text
A --- B --- C --- D --- E
                      main
                      feature
```

Это называется **fast-forward**.

На текущем этапе достаточно понимать:

```text
merge
→ иногда создаёт merge commit
→ иногда может просто передвинуть указатель
```

---

# 24. Rebase

Есть другой способ обновить feature относительно нового `main`.

Допустим:

```text
A --- B --- C   main
       \
        D --- E   feature
```

Вместо merge можно выполнить rebase.

```bash
git rebase main
```

Git берёт изменения из:

```text
D
E
```

и переигрывает их поверх:

```text
C
```

Получается:

```text
A --- B --- C --- D' --- E'   feature
```

---

## Почему D превращается в D'

Commit определяется не только изменениями.

В него входят также:

- parent;
- metadata;
- содержимое.

Раньше:

```text
D.parent = B
```

После rebase:

```text
D'.parent = C
```

Это уже другой commit.

Поэтому:

```text
D ≠ D'
E ≠ E'
```

и hashes меняются.

---

## Что делает rebase концептуально

Можно сказать:

> Представим, что feature изначально началась не от B, а от свежего C.

До:

```text
A --- B --- C
       \
        D --- E
```

После:

```text
A --- B --- C --- D' --- E'
```

История стала линейной.

---

## В IntelliJ IDEA

В Branches / Git actions можно встретить действие примерно:

```text
Rebase Current onto Selected
```

Если current:

```text
feature
```

а selected:

```text
main
```

получаем:

```text
rebase feature onto main
```

---

## Под капотом

```bash
git rebase main
```

### Главное

```text
Merge
→ соединяет истории

Rebase
→ переносит commits
→ переписывает историю текущей ветки
```

---

# 25. Merge vs Rebase

Было:

```text
A --- B --- C   main
       \
        D --- E   feature
```

## Merge

```text
A --- B --- C
       \     \
        D --- E --- M
```

Сохраняется информация:

```text
ветки реально расходились
↓
потом были объединены
```

## Rebase

```text
A --- B --- C --- D' --- E'
```

Получаем более линейную историю.

---

## Сравнение

| | Merge | Rebase |
|---|---|---|
| Объединяет две истории | да | косвенно |
| Переписывает существующие commits feature | нет | да |
| Может создать merge commit | да | нет |
| Делает историю линейнее | не обязательно | да |
| Меняет hashes переносимых commits | нет | да |

### Практическая модель

```text
merge
→ «соедини две дороги»

rebase
→ «перенеси начало моей дороги»
```

---

# 26. Почему rebase часто делают перед Merge Request

Представим, MR уже открыт.

Пока вы работали:

```text
main
```

изменился.

Было:

```text
A --- B   main
     \
      D --- E   feature
```

Потом в main добавили:

```text
C
```

Теперь:

```text
A --- B --- C   main
     \
      D --- E   feature
```

Перед финальным merge удобно обновить feature.

Rebase:

```text
A --- B --- C --- D' --- E'
```

даёт несколько преимуществ:

- feature основана на свежем `main`;
- конфликты решаются заранее;
- история становится линейной;
- MR проще читать;
- часто становится возможен fast-forward merge.

---

## Важная цена rebase

Если `D` и `E` уже были отправлены в GitLab, после rebase там всё ещё находятся старые commits.

Локально:

```text
D' --- E'
```

На remote:

```text
D --- E
```

Обычный push может быть отклонён.

Тогда используется:

```bash
git push --force-with-lease
```

`--force-with-lease` безопаснее обычного `--force`, потому что дополнительно проверяет, что remote branch не изменилась неожиданно.

На курсе force push стоит использовать только осознанно.

# 27. Amend

Иногда commit уже создан, но мы заметили:

- забытый файл;
- опечатку;
- плохой commit message.

Можно создать ещё один commit.

Но иногда хочется исправить именно **последний commit**.

Для этого существует `amend`.

## Было

```text
A --- B --- C
```

После amend:

```text
A --- B --- C'
```

`C` и `C'` — разные commits.

Hash меняется.

---

## В IntelliJ IDEA

В Commit tool window можно включить:

```text
Amend
```

и выполнить commit.

---

## Под капотом

```bash
git commit --amend
```

Если commit уже был запушен, возникает та же проблема переписанной remote history.

Может потребоваться:

```bash
git push --force-with-lease
```

### Главное

```text
amend
→ не редактирует commit на месте
→ создаёт новый commit вместо старого
```

# 28. Merge Request

## Проблема

Feature-ветка уже находится в GitLab.

Теперь нужно:

- показать изменения другим людям;
- получить review;
- проверить CI;
- разрешить возможные конфликты;
- только потом объединить feature с target branch.

Для этого нужен **Merge Request**, сокращённо MR.

---

## Основная идея

```text
source branch
↓
Merge Request
↓
target branch
```

Например:

```text
source:
hw-03

target:
main
```

MR означает:

> Прошу объединить изменения `hw-03` с `main`.

---

## Что происходит при создании MR

MR сам по себе не изменяет `main`.

GitLab:

```text
берёт source branch
+
берёт target branch
↓
сравнивает их
↓
строит diff
```

В MR можно увидеть:

- commits;
- изменённые файлы;
- diff;
- комментарии;
- review;
- CI;
- наличие конфликтов.

---

## Где работаем

Для курса базовая модель:

```text
IntelliJ IDEA
→ пишем код
→ Commit
→ Push

GitLab
→ создаём MR
→ review
→ merge
```

---

# 29. Что происходит, если после создания MR сделать новый Push

MR связан не с конкретным набором commits навсегда, а с source branch.

Например:

```text
hw-03
```

После создания MR вы сделали ещё commit:

```text
A --- B --- C
```

и:

```bash
git push
```

GitLab видит новое состояние `hw-03`.

MR автоматически обновляется.

То есть новый MR создавать не нужно.

# 30. Conflict

Git умеет объединять множество изменений автоматически.

Например:

```text
main
→ изменили строку 10

feature
→ изменили строку 50
```

Обычно проблем нет.

Но если изменено одно и то же место несовместимым образом:

```text
base:
int result = 10;

main:
int result = 30;

feature:
int result = 20;
```

Git не знает:

```text
20?
30?
другое значение?
```

Это **conflict**.

---

## Что означает конфликт

Конфликт — не поломка repository.

Он означает:

> Git не может безопасно решить, какой итог правильный.

Git останавливается и передаёт решение человеку.

---

# 31. Конфликт в IntelliJ IDEA

IDEA предоставляет:

```text
Merge Editor
```

Упрощённо:

```text
Yours
       \
        Result
       /
Theirs
```

Нужно посмотреть:

- что было с одной стороны;
- что было с другой стороны;
- каким должен быть итоговый Java-код.

---

## Нельзя всегда выбирать Yours

Например одна сторона добавила:

```java
int sum = calculateSum(numbers);
```

другая:

```java
int max = findMax(numbers);
```

Правильный итог может быть:

```java
int sum = calculateSum(numbers);
int max = findMax(numbers);
```

То есть:

```text
Yours
≠ всегда правильно

Theirs
≠ всегда правильно
```

Иногда нужно вручную собрать итог.

---

# 32. Conflict при Merge

Было:

```text
feature
↓
merge main
```

Git обнаружил конфликт.

Сценарий:

```text
Merge
↓
Conflict
↓
Merge Editor
↓
разрешить
↓
проверить код
↓
завершить merge
```

CLI-эквивалент:

```bash

```

После исправления:

```bash

git commit
```

Появляется merge commit.

# 33. Conflict при Rebase

При rebase ситуация немного другая.

Git переносит commits **по одному**.

Например:

```text
перенос D
↓
conflict
↓
resolve
↓
continue
↓
перенос E
↓
возможно ещё conflict
```

CLI:

```bash
git rebase main
```

После исправления:

```bash
git add .
git rebase --continue
```

Поэтому при rebase конфликт потенциально может возникнуть несколько раз.

# 49. Итоговая схема

```text
GitLab
↓
Clone
↓
Local repository
↓
Branch
↓
изменение файлов
↓
Diff
↓
Commit
↓
Push
↓
Remote repository
↓
Merge Request
```

Если remote изменился:

```text
Fetch / Pull
↓
обновление локального состояния
```

Если истории нужно объединить:

```text
Merge
или
Rebase
```

Если Git не может объединить автоматически:

```text
Conflict
↓
Merge Editor
↓
решение принимает разработчик
```

> **IntelliJ IDEA делает Git удобнее, но понимание Git-модели остаётся обязательным: repository, commit, branch, remote и история существуют независимо от интерфейса IDE.**
